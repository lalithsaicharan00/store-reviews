# Habit Details — Header, History Actions and Notes: Final UX Pass

Written by Codex (OpenAI), 4 October 2026.

This is a **research and interaction proposal**, with [22 Markdown-renderable screen studies](Wireframes.md) and three editable Figma boards: [habit header, History and Notes](https://www.figma.com/design/Ncccsm1l2O62GJ5xLSInqk/Design?node-id=433-2071), [type-aware recording](https://www.figma.com/design/Ncccsm1l2O62GJ5xLSInqk/Design?node-id=434-2071), and [Notes/quit edge states](https://www.figma.com/design/Ncccsm1l2O62GJ5xLSInqk/Design?node-id=443-2071). It revises the action placement and naming in the earlier [Habit Details package](../README.md). The current month groups, meaningful-day rows and History → Day details → exact-record correction model remain the baseline.

**The Figma screens represent information order, wording and behavior, not finished iOS visuals.** Their symbols, status bar, segmented control, buttons, fields, calendar and More menu are editable proxies. Build them with native SwiftUI/system controls, SF Symbols, semantic colors, Dynamic Type, VoiceOver and the app's light/dark appearance (Rulebook U1/U9). None of these screens has been implemented or tested on an iPhone. This report is research documentation, not the formal decisions document.

## Revision after the user's design review

The first boards gave History and Notes tab-specific **sticky bottom actions**. That made each tab behave like a dedicated page even though both belong to one Habit details page. The accepted revision places actions within each tab's scrolling content. History labels are a small type map, never assembled from the habit name. Notes keeps Add note beside its section heading and Search above the dated list. The note reader keeps Edit note beside the note; an existing-note editor includes a bottom Delete note button with native confirmation. The earlier bottom-bar hypothesis is superseded by the user's direct visual and interaction review.

The first record forms also looked like a separate product surface. The revised forms reuse the accepted [entry editor](<../../Day Structure and Organization/Day Details and Entry Editor Handoff/README.md>) habit identity card, top Save pattern and field hierarchy. Once-daily checks, checklists and skipped days now show the accepted Day-details layouts rather than alternative designs. A new picker frame shows what tapping the record form's date does. This is a design proposal, not an app implementation.

## What changed in this pass

| Surface | Existing app / earlier study | Proposed revision and reason |
|---|---|---|
| Navigation/header | The navigation title repeats the habit name. The icon, name and goal sit in a leading row; streaks are absent. | Navigation title **Habit details** names the destination. Center icon → name → goal and time section; wrap long supporting text. Put **Current streak** and **Best streak** immediately below, as two readable facts. This prevents duplicate names and restores important progress context without putting charts above the tabs. |
| History | Add Entry and Go to Date occupy the first content position. Go to Date's destination is unclear; Add Entry uses generic language and has had contrast trouble. | Keep the chronological month/row content. Put two native-size actions directly inside History, before the month list: **Choose date** and a short label fixed by habit type. Date selection explicitly opens that day's Day details, including an empty day, without logging. Reachability improves while the chronology becomes the first thing read. This placement follows the user's review of the tab layout; it still needs iPhone validation. |
| Recording | One generic Add Entry form is used for amount, time, multi-check, binary, checklist, task and quit; it shows a generic Add control and an entry list. | New-record forms reuse the accepted entry editor's habit card and top Save toolbar, with a selected date before the input and a date picker that returns to the form. Amount, duration, repeated-check and slip save **one separate record**. A once-daily check, checklist step or task uses the accepted Day-details controls for that date. The saved-record editor still corrects one independent fact (U19). |
| Notes list | Add Note is squeezed beside the search field. | Search uses the full width above the notes it filters. **Add note** sits beside the Notes heading, above the full-width search field; it remains available in empty Notes. The month rows still browse by date. Search focus can temporarily suppress the action while the keyboard is up. |
| Note reader | View Day and Delete Note appear as similar list rows beneath the note. | Give the full text its own content area; provide a clearly related **Open day details** row with the exact date and activity context. Keep **Edit note** beside the note content. Put destructive **Delete note** in a nearby native More menu and at the bottom of the existing-note editor; both routes require confirmation. Reading and deletion no longer look like peer destinations. |
| Day-details naming | Different entry points call it View Day, day log or the Day sheet. | Use **Day details** as the product/VoiceOver name and the link label. Keep the existing sheet's prominent selected-day title (Today / a full historical date) and native Close control (U18). The date remains the visible answer to “which day?”; adding another generic header would take space without resolving ambiguity. No Day-details visual change is proposed. |

## Evidence and limits

This pass builds on the repository's reviewed evidence rather than assigning a new count to these mockups:

- [Undo and Fixing Progress — What People Expect](<../../Day Structure and Organization/Undo and Fixing Progress — What People Expect.md>) reports **715 on-topic habit-app reviews across 84 apps** in its selected study; 59 describe filling a past day, 54 changing a past result and 47 correcting/deleting one wrong amount or time record. These are overlapping themes in a selected on-topic set, not user-population rates. They support permanent, exact correction and date access. They do **not** prove that a bottom action area is preferred.
- [Habit History — Research and Recommended Layout](<../Original Reports/Day Structure and Organization/Habit History — Research and Recommended Layout.md>) checked original review evidence and already established meaningful dates, direct date selection, note-only days and date → Day details. This pass preserves those conclusions and changes the two action controls after the user's review of the live layout.
- [Habit Notes — Research and Recommended Experience](<../Original Reports/Day Structure and Organization/Habit Notes — Research and Recommended Experience.md>) and [Habit Notes and Day Notes — What People Ask For](<../../Day Structure and Organization/Habit Notes and Day Notes — What People Ask For.md>) support dated notes independent of completion. They do not establish that note creation deserves equal prominence to recording on the History tab. The full-width search and separate Add note placement are reasoned from the Notes tab's browsing job.
- [Showing the Streak — One Unit Rule, One Place](<../../Home Screen and Visual Design/Today Screen Habit Cards/31. Showing the Streak — One Unit Rule, One Place.md>) found day units dominant in the sampled streak expressions and specific weekly-unit confusion. The habit goal stays directly above the cards, and the cards use the goal's actual unit; they must never silently switch days to months or show an unexplained weekly number. [Milestones on the Habit Page](<../../Day Structure and Organization/Milestones on the Habit Page — What to Mark and How to Show It.md>) already assigns the full milestone record to Progress, so a third header statistic would duplicate that job.
- Apple's [navigation-title guidance](https://developer.apple.com/documentation/swiftui/configure-your-apps-navigation-titles) describes a title as the current navigation state. Apple's [toolbar guidance](https://developer.apple.com/design/human-interface-guidelines/toolbars) supports logical top/bottom action groups and a More menu for lower-priority actions. Apple's [search-field guidance](https://developer.apple.com/design/human-interface-guidelines/search-fields) specifically permits an inline field immediately above the list it searches. Apple's [picker guidance](https://developer.apple.com/design/human-interface-guidelines/pickers) supports native compact/inline date selection. These are platform guidance, not proof of user preference or evidence that the Figma controls are native.

## The header and streak facts

The navigation bar says **Habit details** once; the centered identity says **what this habit is**. Use the actual habit icon, full habit name and the goal/schedule copy from the saved habit rules. The name may wrap; the goal and time-of-day section should wrap to two or more lines under accessibility text sizes instead of shrinking into tiny text. Spacing below the supporting line grows when it wraps, leaving the streak cards clear. The [weekly example](Images/history-weekly.png) deliberately uses two supporting lines.

The two cards answer different questions: **Current streak** (what is active now) and **Best streak** (historical high). Label both with the actual unit: `8 days`, `4 weeks`, `3 months` as applicable. A 3-times-a-week habit earns a streak of goal-met **weeks**, not a day tally. Never silently convert a long run to a different unit. For a quit habit, use **Current run** and **Best run**, using the existing quit-run calculation and a neutral description. A task has no streak cards. Honor the existing **Show Streaks** preference; hiding streaks must remove the cards, not leave empty boxes. For a new habit, a neutral `No current streak` is preferable to turning a zero into a failure message (U3). Pause/skip semantics and past rule changes come from `HabitStore`, not view-side guesses (S5/D6).

Keep the description and paused/resume context if present; this proposal does not delete them (U5). A description can follow the identity as body copy, while a paused banner remains a separate status control. Do not put milestones, charts or a third record card in this header: Progress already contains those facts.

## History: the two actions and the date route

The History tab continues to open on the most recent meaningful dates, grouped by month. The two actions sit directly under History's segmented tab and scroll with its dated list. **Choose date** is a neutral secondary control; the habit-specific record action is the primary control for build/maintain goals and a neutral control for an at-most limit or a quit slip (U16). Both are native-size targets and have meaningful VoiceOver names. Preserve the existing full row tap for a known date and list scroll position on return.

**Choose date** opens a native date picker constrained to the habit's actual recordable range. Its helper text says the selected date opens **Day details** and does not create progress. Show Today/Yesterday shortcuts only if a native, accessible arrangement fits; direct month/year selection is more important than swiping through many days. Selecting an empty historical date opens that exact date with a no-record state. The selected day may be paused, skipped or outside the due schedule; Day details explains it rather than silently substituting the nearest logged date. A date row and the picker never mutate completion (U14).

The second action uses a short, fixed type label, never text generated from the habit name: **Log time** for duration, **Log amount** for a positive amount, **Add check** for repeatable checks, **Record amount** for an at-most limit, and **Record slip** for quitting. It should not present an unexplained generic **Add Entry**. The word *record* can remain in explanatory/history copy where it refers to a saved fact; no single generic CTA has to carry every habit type. For a once-daily check, checklist or task, the action says **Open Day details** or the actual next control, then reuse the selected Day-details screen. The Figma [daily check](Images/daily-check.png) and [checklist](Images/checklist.png) frames duplicate the accepted Day-details designs to make this route unambiguous. Reuse the accepted [Day-details handoff](<../../Day Structure and Organization/Day Details and Entry Editor Handoff/README.md>).

Build these controls inside History's scroll content, below the segmented tab and above the first month. Check localization, VoiceOver, accessibility sizes and short devices on an iPhone. The two actions must remain distinguishable when labels localize or enlarge; stack them if needed rather than shrinking type. This placement is a proposal to test, not a measured preference.

## Recording: one selected date, then the habit's fact

The default tracking day is Today when opened from History. A past-day History row or Choose date passes its exact selected date. In a focused record form, the date appears before the value and can be changed before saving. Tapping it opens the illustrated picker; **Use date** returns to the same unsaved form. The native top **Save** adds one record. An additive form saves **one new record**, never replaces the day's total. Keep an existing-day summary only when it prevents ambiguity; a long list of saved records belongs in Day details. After Save, return to the exact selected Day details or History position and show the updated result. Save is disabled when the selected-day state does not allow a record; do not secretly preserve Skip while enabling a conflicting log (U15). Undo skip stays in the Day sheet at its original control.

| Habit | Focused input/action | Save meaning and correction route |
|---|---|---|
| Positive amount | Number plus saved unit; today/past uses the same form | `Save` adds one glass record. Day details shows each record; the single-record editor changes one amount. |
| At-most amount | Same value control, native top Save action | Available without promoting another unit of a limited behavior; no success claim just because consumption was logged. |
| Duration | Native, directly editable hours/minutes (and seconds if the domain permits) | `Save` adds a separate manual session. Timer sessions stay distinct. The record editor permits precise correction without changing other sessions. |
| Repeated check / weekly count | Native stepper or count field, initial value 1 | `Save` adds one count record on the selected day. A bulk count is **one** saved record, not several invented timestamped events. |
| Once-daily check or task | Existing selected Day-details check control | Mark done/undo there. Do not create a redundant `Times 1` entry editor (U19). |
| Checklist | Existing selected Day-details named step controls | Change a named step there; do not create a generic “entry” for the whole checklist. |
| Quit | Native date **and occurrence-time** picker; fixed History label **Record slip** | Save records when it **happened**, not when it was saved. The single-slip editor can later correct its occurrence date/time or remove exactly that slip (U19). |

Backfilled amount and duration records may truthfully say **Added now for 2 Oct**; their creation timestamp must not masquerade as the event time. The chosen tracking date belongs to the user-visible row. A slip is different because its occurrence time is an actual field. Historical units, goals, habit start, pause and skip rules must come from the rule effective on that date (D6/D7/U19). The [recording board](https://www.figma.com/design/Ncccsm1l2O62GJ5xLSInqk/Design?node-id=434-2071) shows the main routes and a skipped-day conflict state, but its inputs are schematic; use native keyboard/picker behavior.

## Notes: browse, read, write, move to day

Search remains at the top of the **Notes** tab and filters only this habit's notes. It gets a full-width field with a native clear action. The month rows and previews remain newest first. Empty Notes needs an explanation and Add note action; an empty search result says no notes match and offers a clear-search route. Search must not change the saved notes. Retain the existing debounced search behavior (S11).

**Add note** is separate from search and sits beside the Notes heading while browsing. It opens a native multiline editor with Today selected by default and a visible date that can be changed before Save. If the selected date already has a note, open it for editing or make replacement explicit; do not silently overwrite another day's note. Cancel on a dirty draft confirms discard. Save is disabled for a blank note if blank is treated as deletion; keep current note semantics consistent. The note belongs to habit + day independently of progress, and entry deletion must not remove it (U5/D7).

In the reader, the exact full date is primary, the habit name is secondary context, and the note text has a content-sized reading area and text selection. **Edit note** stays directly visible beside the note content. **Open day details** is a separate related-day row with that exact date and, when known, the day's nonjudgmental activity summary. It opens the shared Day-details sheet **for the note's date**, even if the day has no progress. Its accessibility label should include the date, for example “Open day details for Sunday, 4 October 2026.” A nearby native More menu holds **Delete note**. The existing-note editor also shows a bottom destructive Delete note button, while new-note creation has no Delete action. Either deletion route presents the same native confirmation and only then removes this note. Other notes, habit data and progress stay intact (D6/U14).

### Name the shared destination consistently

Use **Day details** in links, VoiceOver labels and implementation documentation. The visible selected-day title of the sheet can stay **Today** or the selected calendar date because that is more useful in place than another generic heading. A note reader already displays the full date, and the sheet should show that same date when it opens. Do not add a second day picker or bottom pager to the sheet solely to support this link: the selected date arrives from the link, and the previous [Day-details spacing/action study](<../../Day Structure and Organization/Day Details and Entry Editor Handoff/The Habit Day Sheet — Wording, Hierarchy and Actions.md>) removed that pager for a reason. No Day-details wireframe changed in this pass.

## Native implementation and validation contract

The current code points are `HabitPageView.swift` (header, navigation title, menu and routes), `HabitPageParts.swift` (History/date picker), `AddEntryView.swift` (type-aware form), `HabitNotesTab.swift` (search, note reader/editor) and `HabitStore` (streaks, historical rules and saved records). The present app still uses a generic Add Entry sheet and top History actions. These mockups are **not a statement that those changes are already shipped**.

Before implementation, preserve all current behavior (U5): the History month/day content, direct past-date access, date-specific Day details, edit/pause/archive/delete management, note search, date-scoped notes, and exact-record correction. Use the existing **Show Streaks** setting. A top-right native More menu still owns habit management; the note reader's More menu owns only note actions. Do not mix those scopes. Buttons and date fields must have at least native hit areas, meaningful accessibility names, semantic colors and disabled states (U1/U14/U16). The proposal's blue Figma button is **not** a mandated custom style.

Validation jobs for the later implementation: (1) from a weekly habit, understand `4 weeks` beside its goal; (2) find an empty date two years back without changing it; (3) add to yesterday without replacing its prior records; (4) undo a skipped day before logging; (5) open a note's day and see the same date; (6) search a long Notes list and add a note for a different date; (7) check long names, localization, light/dark, Dynamic Type, VoiceOver, keyboard and the home indicator on a real iPhone. These are proposed usability/runtime checks, not completed results (U9/T3/T4).
