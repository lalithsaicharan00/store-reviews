Written by Codex (OpenAI), 4 October 2026. This translates the [31 wireframes](README.md) into behavior for the iOS app. It records implementation intent, **not an assertion that the current app already works this way**. Read [Rulebook](<../../../../RULEBOOK.md>) and [Design Rules](<../../../../iOS/Design Rules — Don't Regress.md>) first (U1/U12).

## The boundary between Figma and iOS

The Figma pop-ups are **layout and interaction representations, not final designs**. Reuse the existing app's native SwiftUI surface, semantic colors and system typography. Do not import the PNGs into the app or recreate the glyphs as static text. The screenshot dimensions and 48/44 pt button specimens communicate *relative size and tap-area intent*, not a fixed layout at every phone size. Native controls must remain usable at accessibility Dynamic Type sizes, in both appearances, and through VoiceOver (U1/U9). Build each control to mean what it looks like; a chevron navigates, a button acts, a note surface opens note editing and a disabled logging action remains visibly unavailable.

## Day-details state model

1. **Identity and date:** toolbar describes the selected day; identity row describes the habit/plan once. Remove only the redundant bottom pager, not access to previous days (U5). Reach a past-day sheet through Today or the habit calendar. Periodic goals show selected-day status separately from week/month total.
2. **Activity:** render the natural action per type. Binary and one-time task: Mark done or Undo done. Repeated checks: Add a check and named correction of an existing check. Checklist: its named steps. Positive amount: quick add plus manual amount. Limit: factual quick/manual recording without positive-goal emphasis. Duration: Start timer plus manual time; saved sessions may be edited. Quit: Record a slip and show slips when present. The existing home-row CTA remains the fastest action.
3. **Records:** do not show an empty “Today's logs” area. Show saved amount/time/slip/check records only when there are actual records. A log row opens the one-record editor when its value or occurrence can be meaningfully changed; a single check corrects directly. Preserve individual undo (U14/U19).
4. **Note and exception:** note follows the day activity because it describes that day; Skip follows at a larger separation because it changes eligibility. Skipping never removes previously recorded facts or a saved note. Notes are still editable. Pause is a habit-level state and should be described neutrally (U3/U15).
5. **Management:** keep habit management in one native menu. The visible habit identity row handles navigation; Edit, Pause/Resume, Archive and Delete are menu commands. Destructive action last and confirmed. A task identity has no habit-page navigation; task editing and deletion are task-specific menu commands. One-time task date and Do Tomorrow remain visible in the sheet while unfinished.

### Task note boundary

The [task-note review](<Task Notes in Day Details — Evidence and Decision.md>) supports an optional note surface for tasks, including after completion, with less visual weight than Mark done/Undo done. `HabitStore.setNote(_:of:on:)` saves under task ID plus day, and `DaySheet.moveTask(to:)` changes only the due date. Keep the honest **Note for this day** wording in this implementation pass. If a future design needs one-time task instructions to follow rescheduling, first define and test the store, persistence, backup and sync migration; do not silently lose or mislabel the existing date note (D7/U5). No task entry editor or Skip action is introduced by these wireframes.

## One-record editor and storage model

- **Amounts:** edit the selected value with unit and locale-aware decimal validation; preserve source and tracking day. Positive amounts only; no silent rounding or value clamp. A limit's factual correction should not inherit positive-goal celebration.
- **Durations:** present Hours, Minutes and Seconds together. On open, keyboard stays closed. Tapping a part selects its value for direct typing; Hours/Minutes use numeric keypad, Seconds decimal keypad. Next/Done follows logical order; 1.23 seconds must persist. Validate 0–59 Minute/Second parts, total > 0 and the model's maximum near the field. Keep each field's typing state local for S11.
- **Multi-check records:** edit a positive integer only when one record stores a multi-check count. A one-check record has no meaningful smaller positive count; correct it by named one-record Undo in Day details.
- **Quit slips:** edit the **occurrence date and time**, in the saved recording time zone. Changing one component retains the other. Validate actual instant against future/start limits and derive the tracking day using the local calendar/day-start rule, including DST (D7). Current `HabitStore.editEntry` only permits changes within the original day and current repository write only changes timestamp/value; the cross-day UI must wait for atomic update of `createdAt`, `entry.day`, per-day indexes, persistence/sync, affected summaries and quit run under the same ID. After Save, show the destination day with the slip visible; the old day's note remains there.
- **Deletion:** one selected ID only. Show explicit **Delete this log** or **Delete this slip** as a bottom native button, separated from Save and the field without a divider. On tap, present a native alert naming the record/day with Cancel and a destructive confirmation; no delete runs on initial tap. Confirm while there is no durable one-record Undo. Saving/deleting one record recalculates day status but preserves other logs, note and skip flag. Keep the button in the editor's scroll/safe-area layout and reachable after dismissing a numeric keyboard at Dynamic Type sizes.

## Why this is the handoff, and what remains open

The user accepted the revised overall layout after the later size, Skip, note, spacing and Close corrections, and accepted the one-record editor direction while requesting a clearer time-input and slip-occurrence model. The [decision history](<Decision History — Why the Layout Changed.md>) explains each revision. The design improves scan order and action meaning by first principles and platform guidance; exact copy and spacing have not been user-tested. In particular, “log” terminology remains a hypothesis.

Before marking the implementation complete: update relevant UI tests when labels change (T3), add screen/interaction performance scenarios and measure them (S2/T4), run the repository's `check_rules.sh`, verify data moves and offline persistence (D1/D7), and inspect the real iPhone in light/dark, large Dynamic Type, VoiceOver, keyboard and past/skipped states (U9). Avoid performing those gates on documentation-only work; the current app is unchanged by this handoff.
