# 08. Release Safety and Operations

*Written by Claude (Claude Code), 26 Sep 2026. Topic 8 of the [architecture list](README.md). A proposal, not yet built.*

**Scope:** everything that stops a new version from hurting people, and what we do when something goes wrong anyway. It covers:
- local database migrations;
- staged rollouts;
- kill switches;
- crash-loop recovery;
- new OS versions and old devices;
- redesigns and removed features;
- never taking away what someone has;
- update prompts;
- the data-loss canary;
- support tools;
- telling users about incidents.

**Already decided** in [Data Safety, Accounts and Sync §5–6](<Data Safety, Accounts and Sync.md>):
- the five safety nets;
- no destructive migrations;
- additive schema only;
- migration tests on every shipped version;
- the convergence test;
- the canary's basic idea;
- phased releases.

The server side (gradual deploys, lazy per-account upgrades) is in [06 §8](<06. Server on Cloudflare.md>). This doc adds the app side and operations.

**How each rule is backed:**
- **Users show**: backed by review evidence.
- **Platform rule**: an Apple or Google requirement or behaviour, with a link.
- **First principles**: reasoned from how the system works.

**Evidence:**
- **A fresh screen:** 1,487,223 reviews, 10 release patterns, 5,840 matches. These are the angriest patterns in any topic so far: "crash on open" 68.5% one-star, "no support reply" 78.6%, "update wiped" 70.2%.
- **206 read in full and coded,** with quotes verified. 156 are about this topic; the rest are mostly billing complaints, covered in topic 2.
- **Files:** [`Release Evidence/`](<../Research/Research Reports/Data, Sync and Accounts/Release Evidence/>).

## 1. The design on one page

1. **An update may change how things look, never what the user has.** Their data, history, streaks, paid features and free features all survive every update (users show: 21 "update wiped" reviews, mean 1.8; 12 "update put what I had behind a paywall", mean 1.8).
2. **Every release is staged:** internal → TestFlight / closed testing → 1% of users → 100% over a week. Watch the crash-free rate and the data-loss canary at each step, and halt on any regression.
3. **We can switch things off without an app update.** Remote flags turn off any new feature, the sync, or a migration step within minutes.
4. **A crash loop can't lock anyone out.** After two crashed launches, the app starts in **safe mode**, showing the data read-only with export and "restore yesterday's copy". It never tells users to reinstall (users show: “I had to delete the app and reinstall it.. I lost everything.” (`P84#10761`)).
5. **We test on the next OS before it ships.** Every June beta and every September release, on the oldest and newest supported devices (users show: 17 reviews of an OS update breaking the app).
6. **Redesigns are opt-in first.** A big layout change ships behind a switch ("Try the new Today"). The old layout stays for at least one release, and nothing the old one did disappears (users show: 22 reviews begging to go back, 14 redesign complaints).
7. **Never a forced update that blocks data.** The oldest app version the server accepts is at least 12 months old. Even an app below that opens, shows everything, and exports.
8. **Every support message gets a human reply within 1 working day,** from a support tool that can see sync state, restore an account and re-grant a purchase (users show: 20 "no reply" reviews, mean 1.8, against 7 praising fast help, mean 4.7).
9. **When something breaks, we say so first:** an in-app banner, before the reviews arrive. No email: we send only the purchase confirmation (topic 1 §3.8).

## 3. Local database migrations (the app side)

The main doc bans destructive migrations. The rules here say **how** a migration runs:

1. **Before migrating,** take a snapshot of the database file (net 2) and record the old schema version.
2. **Run the migration in one transaction.** If anything fails, roll back: the app keeps running on the old schema, in a "needs update" state. It shows its data, can't use the new feature, and sends us the error.
3. **After migrating,** run the canary check (§6). If counts don't match, restore the snapshot automatically, stay on the old schema, stop syncing, and report.
4. **Keep the pre-migration snapshot for 30 days,** and "Restore from before the update" in Settings → Backup.
5. **Heavy migrations run in the background** after the first screen appears. The user never waits on a spinner (topic 6 users: slow start).
6. **Never ask the user to export and import** to move to a new version (users show: `P111#1118`, `P31#19`).
7. **Migration tests** run on a saved database from **every shipped version**, plus a set of "ugly" databases:
   - 10 years of entries;
   - 500 habits;
   - emoji names;
   - every time zone;
   - a half-finished earlier migration.

## 4. Staged releases, flags and halting

### 4.1 The release path

| Stage | Who | How long | Go on if |
|---|---|---|---|
| Internal | us, on our real data | 2+ days | no crash, canary clean |
| Beta | TestFlight / Play closed testing, opt-in users | 3+ days | crash-free ≥ 99.8%, canary clean |
| Phased 1% → 100% | App Store phased release (1, 2, 5, 10, 20, 50, 100% over 7 days) and Play staged rollout | 7 days | crash-free and canary at or above the previous version |

- **Apple:** phased release can be paused for up to 30 days, but anyone can still update by hand from the App Store ([Apple](https://developer.apple.com/help/app-store-connect/update-your-app/release-a-version-update-in-phases/)). So pausing slows harm; it doesn't stop it.
- **Google:** halting a staged rollout stops new users getting it. People who already have it stay on it, and there is no rolling back: the fix is a new release ([Google](https://support.google.com/googleplay/android-developer/answer/6346149)).
- **So neither store lets us undo a bad build.** That makes the remote flags (§4.2) and safe mode (§5) essential, not nice-to-haves. *Platform rule.*

### 4.2 Remote flags (kill switches)

A small signed JSON file, fetched by the app at launch and hourly from our server (topic 6), cached on the device. With no network, the last cached copy is used.
- **Per feature:** `new_today_layout: off` hides a new screen and restores the old one.
- **Per migration step:** `migration_14: hold` makes new installs skip a risky step until a fix ships.
- **Sync:** `sync: pause` for a given app version, to stop a bad client from writing bad data to the server. The client keeps its outbox (topic 5), so nothing is lost.
- **Banner:** a short message for everyone or one version (§9).

Flags can only **turn off or hold**. They can't turn on code that wasn't tested, and they never delete anything.

### 4.3 Hot-fix path

- Keep a release branch for the live version, so a fix can ship without whatever is on main.
- Ask Apple for an expedited review for data or crash bugs.
- Target: flag within 1 hour, fixed build submitted within 24 hours (users show: fixes that took days, `A10#7868`).

## 5. Crash-loop recovery (safe mode)

**Detection:** at launch the app writes `launch_started`. When the first screen has been shown and the database has opened, it writes `launch_ok`. If the app starts and finds two `launch_started` markers in a row with no `launch_ok`, the last two launches crashed.

**Safe mode** (third launch):
- skips everything optional: widgets refresh, sync, Health import, animations, the latest migration's background work;
- opens a simple screen: "Something went wrong with the last update. Your habits are safe." with:
  - **See my habits** (read-only list and history);
  - **Export a copy**;
  - **Restore yesterday's copy** (local snapshot, net 2);
  - **Send a report to us** (diagnostics, no habit content unless the user ticks "include my data");
  - **Try again normally**.
- It never offers "reinstall", because reinstalling is how people lose data (users show: `P84#10761`, `A48#4081`).

**Crashes caused by the user's own data** (users show: `A24#16457`, `A10#25319`) are why "Send a report" can include the database with permission. That turns an unreproducible bug into a fixable one.

**No scary wording.** Never "your data is corrupted". Say what we'll do: "We couldn't open part of your data. We've kept a copy and can restore yesterday's." (users show: `A10#33396`).

## 6. The data-loss canary (detail)

Checked on the device after every migration, restore and sync that pulls changes:
- number of habits (not deleted);
- number of entries in the last 90 days;
- the latest entry date;
- current streak per habit (recalculated, so it's a check on the calculation code, not on stored data).

**Trigger:** any count that drops by more than 10% (or by 5+ habits) without matching user deletes or tombstones.

**Response:**
1. Keep the snapshot from before the change.
2. Pause sync for this account (so the drop can't spread to other devices or the server).
3. Show a calm banner: "Something changed that we didn't expect. Your data is saved; we're checking it." with a button to restore the previous copy.
4. Send `data_drop_detected` with the app version, the step and the counts (no content).

The **server runs the same check** when it applies a batch of ops (topic 6): a batch that deletes most of an account is held for review, and the client is told to keep its outbox.

**Release gate:** any `data_drop_detected` from a new version during phased release pauses the rollout until explained.

## 7. New OS versions and old devices

- **Every June:** install the iOS and Android betas on test devices and run the full test suite and a day of real use. Fix before September (users show: `A27#109`, `A13#11806`, `A23#4575`).
- **Every September:** release a verified build on OS launch day, or confirm the current one works.
- **Supported versions (decided 28 Sep 2026):**
  - **iOS 18 and later** (about 88% of iPhones in mid-2026; iOS 26 is ~70%) and **watchOS 11 and later**;
  - **Android 8.0 (API 26) and later** (about 93% of Android devices; Android 10 would reach ~87%) and **Wear OS 3 and later**;
  - Health Connect needs a newer Android and is simply hidden where unavailable.
  - This is the usual production choice: the current major version plus one before it on iOS, and about 90–95% reach on Android.
  - Reviewed every year, and announced in the app two months before dropping one.
  - Sources: [TelemetryDeck iOS versions](https://telemetrydeck.com/survey/apple/iOS/majorSystemVersions/), [Android distribution](https://capgo.app/android-distribution-chart/).
- **Dropping an OS never strands data:** the last version for it keeps working (offline, export, backup). The server keeps accepting its protocol for 12 months (topic 6 §8) (users show: `A33#2521`, `P97#2860`).

## 8. Changing the product without betraying anyone

**Never take back what people have.** Apple's guideline 3.1.2(a) says that when an app moves to subscriptions, existing users keep the primary functionality they already paid for. Reviewers quote it back at developers (`A20#1213`). Our rule is stricter:
- **Paid:** anything someone paid for stays theirs forever: Plus lifetime, or whatever a past purchase unlocked (topic 2).
- **Free:** a feature that was free when someone started using it stays free **for them**. New users may get the new limits; existing users are grandfathered. This is enforced by a "rules version" stamped in the local database at first launch (free users have no account) and copied to the account if they later buy Plus. The free limit of 5 habits is set so it never has to change (topic 2 §3.1) (users show: 12 paywall-on-update reviews, `P20#159`, `P114#9`).
- **Warn before, not after:** any change to what's free or paid is announced in the app a release ahead, in plain words (users show: `A33#116`).

**Redesigns:**
- ship behind "Try the new …" for at least one release, with a one-tap way back;
- beta testers see it first;
- **nothing the old layout did may be missing** in the new one. Check it against a feature list before release;
- only then make it the default, with "Switch back" still in Settings for a while (users show: `A13#14776`, `P110#1486`).

**Removing a feature:** only with a replacement, or with an export of anything it held, and a release's notice. Widgets, notification actions and Watch features are included (users show: 11 feature-removed reviews; topic 7).

**Update frequency:** no more than one release a week except hot-fixes. Auto-update does the rest; we never nag (users show: “I have to update the app every single time I need to use it!” (`N9#37822`)).

## 9. Support and incidents

### 9.1 Support

- **In the app:** Settings → Help → "Contact us". It attaches a diagnostics file (app and OS version, sync state, last errors, account ID; no habit content unless the user ticks the box).
- **After sending,** the app shows "Thanks, a person will reply within 1 working day" (users show: `P122#17400`). The human reply goes to the address the user gave. This answers their own message; it isn't an app email (topic 1 §3.8).
- **Where it lands:** a shared support mailbox on our domain (decided 28 Sep 2026). A help-desk service only if volume grows.
- **A support console** (a small web page on Cloudflare, behind our own sign-in):
  - look up an account by ID or sign-in email;
  - see devices, last sync and outbox errors;
  - see purchases and re-grant them (with an audit note);
  - restore the account to a point in time (topic 6 §9);
  - send a one-off in-app message to that account.
- **No reply templates that dodge the question.** If we can't help, say why and what the user can do.
- **Reply to store reviews** that report bugs, pointing to the fix.

### 9.2 Incidents

| Severity | Example | Tell users |
|---|---|---|
| **Data risk** | a build that may lose data | pause rollout; flag off; in-app banner to affected versions; a written follow-up within 7 days (in the app and in store review replies) |
| **Broken** | crash loop, sync down | banner; hot-fix |
| **Degraded** | slow sync | the Settings status line only |

The in-app banner comes from the remote flags (§4.2), so it reaches even people whose sync is down. Tell users **before** they notice where we can (users show: `A1#51120` "App deletes data without warning").

## 10. Test checklist

- Upgrade from every shipped version's saved database → no count changes; canary clean.
- Kill the app mid-migration → next launch is on the old schema with all data, or completes the migration; never empty.
- Force a migration failure → the app runs on the old schema with a "needs update" note; the error is reported.
- Two forced crashes at launch → the third launch is safe mode; export and restore work.
- Flag a new layout off remotely → the old layout returns on next launch with no data change.
- Flag `sync: pause` for a version → that version keeps its outbox; nothing lost once unpaused.
- A server batch that deletes 90% of an account → held; the client keeps its outbox.
- An install made before a free-limit change → keeps the old limit after the update.
- Run a full release rehearsal on TestFlight and Play internal testing, including halting.
- Remove network, then launch → the cached flags are used; the app works.
- A support restore of a test account → the user's newer edits kept (topic 6 §9).

## 11. Decided later questions

Decided 28 Sep 2026:
- **Free limits never shrink:** the 5-habit free limit is fixed forever, so no grandfathering scheme is needed (§8 still protects anything paid).
- **Supported OS versions:** iOS 18+, watchOS 11+, Android 8.0 (API 26)+, Wear OS 3+ (§7).
- **Crash reporting: Sentry's free tier.** It is needed for crash-loop recovery and the canary, and it covers iOS, Android and the Worker in one place. It sends no habit content.
- **Analytics: PostHog, EU cloud,** content-free, with an off switch (topic 9 §6).
- **Support: a shared mailbox plus our console** (§9.1).
