# 05. Sync Engine

*Written by Claude (Claude Code), 26 Sep 2026. Topic 5 of the [architecture list](README.md). A proposal, not yet built.*

**Scope:** how data is stored on the device and kept the same across devices. It covers:
- the data model;
- the outbox;
- conflicts, deletes and duplicates;
- what a "day" and a "week" are (time zones, day start, week start);
- editing a habit without rewriting its past;
- Health imports without double counting;
- widgets and the Watch;
- when sync runs, and how the user sees it.

The server side (Durable Object, storage, cost) is topic 6. The transport basics (`POST /sync`, 3-second debounce, cursor, acknowledgement) are already in [Data Safety, Accounts and Sync §3.2](<Data Safety, Accounts and Sync.md>). This doc does not repeat them.

**Builds on:** [01 Accounts](<01. Accounts and Identity.md>), [03 Backup](<03. Backup and Restore.md>) and [04 Phone Migration](<04. Phone Migration.md>).

**How each rule is backed:**
- **Users show**: backed by review evidence.
- **Platform rule**: an Apple or Google requirement, with a link.
- **First principles**: reasoned from how the system works.

**Evidence:**
- **A fresh screen:** 1,487,223 reviews, 12 sync and date patterns, 2,539 matches.
- **242 read in full and coded,** with quotes verified. 170 are about this topic.
- **Files:** [`Sync Evidence/`](<../Research/Research Reports/Data, Sync and Accounts/Sync Evidence/>).

## 1. The design on one page

1. **The device is the source of truth for what the user did.** Every tap is written to local SQLite first. The app never waits for the network (users show: offline-created items get "a warning sign").
2. **Every record has a permanent ID made on the device** (UUIDv7). Retries, restores and merges can then never make a second copy (users show: duplicates, 18 of 170).
3. **What happened is stored; what it means is calculated.** Check-ins are stored. Streaks, week progress, totals and "done today" are always recalculated from them and never synced (users show: streak numbers that disagree with the calendar).
4. **Editing a habit never rewrites its past.** Schedule and target changes get an effective date. Old days are judged by the rules that applied then (users show: editing "erases all your past accomplishments").
5. **A day belongs to the person, not the server.** A check-in stores the local date it counts for, and the time zone. It never moves when they travel. The day can start at a custom hour (users show: people who finish "after midnight").
6. **Week start is a setting, default from the phone's region.** All seven days are offered, and every week number, chart and widget uses it (users show: 22 reviews, the largest single theme).
7. **Deletes are records too** (tombstones). A deleted item can never come back from an older device (users show: "deleted habits and routines would reappear on their own").
8. **Conflicts merge field by field.** Changing the name on the phone and the colour on the iPad keeps both. Check-ins from two devices both count once; the same check-in twice counts once.
9. **Health data is read through the platform's merged totals.** It is stored with its source ID, so the Watch plus the phone never count twice (users show: "double counting from iPhone and the Apple Watch").
10. **Widgets, the Watch and shortcuts write through the same outbox** as the app. There is one write path (how, on iOS, is in [07 §3.1](<07. Other Surfaces.md>)).
11. **Sync is visible and can be forced.** A quiet "Synced 2 min ago" line, pull to refresh, and a clear offline state (users show: "I have to kill the app to force a sync").

## 3. Data model

### 3.1 Tables

All tables live in one SQLite file per device (GRDB on iOS, Room on Android). The same schema is used on the server (topic 6).

| Table | One row per | Key fields |
|---|---|---|
| `habit` | habit | id, name, icon, colour, type (yes/no, count, duration, quit), section, order, archived_at |
| `habit_rule` | version of a habit's schedule and target | id, habit_id, **effective_from** (local date), schedule, target, unit |
| `entry` | one thing the user logged | id, habit_id, **day** (local date it counts for), value, created_at, tz, source, source_id |
| `section` | group on Today | id, name, order |
| `setting` | synced preference | key, value (week start, day start, …) |
| `tombstone` | deleted record | table, id, deleted_at |
| `outbox` | change not yet acknowledged | op_id, table, id, fields, hlc |

Every row also carries `hlc` (hybrid logical clock), `updated_by` (device ID) and `schema` (the version that wrote it).

- **IDs are UUIDv7**, made on the device ([RFC 9562](https://www.rfc-editor.org/rfc/rfc9562)). They sort by time, so indexes stay fast, and they never collide across devices. *First principles.*
- **Never a server-assigned ID** and never an auto-increment integer in anything that syncs. An offline device must be able to create a record that is final the moment it's made (users show: `P8#1500`).

### 3.2 Entries are events, not a "done" flag

Each tap is its own `entry` row with its own ID.
- A yes/no habit is done on a day if at least one entry exists for that day.
- A count habit's day total is the **sum of distinct entries**.
- Undo deletes that entry (with a tombstone).

**Why:** two devices adding a glass of water at the same time both count, because they are two different IDs. The same entry sent twice (retry, restore, re-import) counts once, because it's the same ID. A "done = true" flag can't tell those two cases apart. *First principles; users show double counting (`A48#4184`) and lost ticks.*

A double tap within about a second on the same device is treated as one tap in the UI, before anything is written (users show: “there can appear a double notification which makes things count double” (`P12#118071`)).

### 3.3 Calculated, never stored

These are **always** recalculated from `entry` and `habit_rule`, on every device, by the same shared code:
- streaks (current and best);
- "done today", "N left";
- week and month progress;
- totals, percentages and charts;
- widget and Watch numbers.

They are never synced and never saved as the answer. A cache is fine, but it is thrown away whenever a relevant entry or rule changes.

**Why:** when a stored streak and the calendar disagree, users trust the calendar and blame the app (`P7#520`, `N5#15567`, `P33#959`). With one calculation there is nothing to disagree. It also makes "Fix a past day" (§3.5) safe: the streak simply recalculates.

The streak and progress code is written once in the Kotlin Multiplatform core, documented in the behavior contract, and checked with shared fixtures through each supported platform caller. This is the [accepted shared-core decision](<Shared Core Decision.md>), including shared merge rules and native storage/transport adapters. Week progress only counts days that have happened (users show: “taking into account days that haven't passed yet” (`A48#89`)).

### 3.4 Editing a habit: rules with effective dates

Changing the schedule, target or unit **adds a new `habit_rule` row** from today (or a date the user picks). It never edits the old one.
- Past days are judged by the rule in force on that day.
- The editor says so in plain words: "From today, 5 days a week. Earlier weeks keep 3 days a week."
- Changing the name, icon or colour just updates the habit; that has no effect on history.
- Nothing in the edit screen ever deletes entries. The only way to delete history is to delete the habit, with a confirmation and 30-day undo.

*Users show:* seven reviews say editing wiped history or threatened to (`A13#10540`, `A1#47967`, `P2#996`). The one reviewer who got it right praised it (`P24#7965`).

**Recurring items never vanish.** A schedule is a rule, not a list of generated future rows. So there is nothing to "run out" or be lost when the app updates (users show: “One of my repeat weekly 3x habit just disappeared with the new UI” (`A13#13743`); 14 recurring reviews).

### 3.5 Fixing a past day

Any past day can be logged or un-logged, for free, from the habit's calendar and from the day switcher (users show: 15 reviews; paywalled in one (`P7#497`)).
- The entry gets `day` = the day being fixed, and `created_at` = now. Nothing about today changes (users show: `P49#560`).
- The streak recalculates (§3.3).
- If the day is before the habit existed, it is allowed but asked once ("This is before you started the habit. Log it anyway?"), because people do backfill when they start (`A5#194`).

## 4. The day: dates, time zones, day start, week start

### 4.1 An entry belongs to a date, not an instant

Each entry stores:
- `day`: the local calendar date it counts for (e.g. `2026-09-26`), decided **on the device at the moment of logging**;
- `created_at`: the UTC instant;
- `tz`: the IANA time zone then (e.g. `Europe/London`).

Once written, **`day` never changes by itself.** Flying to Tokyo doesn't move yesterday's run to a different day, and a device in another time zone shows it on the same date (users show: “my entire log history was messed up at least 3 times” (`A33#3089`) after travel). *First principles.*

"Today" is always calculated from the device's current time zone and the day start (§4.2).

### 4.2 Custom day start

**Asked in onboarding** (decided 28 Sep 2026): "When does your day end?", default midnight. Any time from 00:00 to 12:00 in 30-minute steps, so night-shift workers are covered. It can be changed later in Settings.
- Taps before that time count for the previous day, and the Today screen still shows the previous day.
- It is shown on the Today title ("Thu 25 · until 3:00") while it applies, so it's never a surprise.
- It's stored with the data: on the phone for free users, and synced to every device for Plus with an account.

*Users show:* 15 day-boundary reviews, including shift workers (“My work day overlaps a day change” (`P8#9539`)) and praise for a 5 am reset (`A1#47683`). Fixed choices were not enough (`P12#15922`).

### 4.3 Week start

- **Asked in onboarding** (decided 28 Sep 2026): "Which day does your week start on?", pre-selected with the phone's regional first weekday (`Calendar.current.firstWeekday` on iOS; `WeekFields.of(locale)` on Android). Changeable later in Settings.
- Any of the seven days.
- One shared function decides "which week is this date in". Every week view, week target, chart, widget, export and reminder summary calls it. No screen assumes Sunday or Monday (users show: settings that apply to one screen only, `A43#124`, `P124#388`, `P3#11497`).
- Changing it changes how weeks are *grouped*, never any entry.

### 4.4 Reminders and time zones

Two kinds, chosen per reminder, default "local time":
- **Local time** ("8:00 wherever I am"): the reminder stays at 8:00 on the clock after travel (users show: `P84#10099`, `A48#4193`).
- **Fixed time** ("8:00 London time"), for things like medication tied to a home clock.

Reminders are re-scheduled on every launch, on time-zone change (`NSSystemTimeZoneDidChange` / `ACTION_TIMEZONE_CHANGED`) and after a daylight-saving change (users show: an hour off after DST, `N1#21139`). Daylight saving is handled by always scheduling from local wall time, never by adding 24 hours.

## 5. The outbox

Recap: each change writes the row and an `outbox` row **in the same transaction**. The sync client sends outbox rows and deletes them only after the server acknowledges (full rules in [Data Safety §3.2](<Data Safety, Accounts and Sync.md>)).

Rules this topic adds:
- **One op per changed field set.** An edit sends only the fields that changed, each with its HLC. That makes the per-field merge (§6) possible.
- **Op IDs are the idempotency key.** The server stores applied op IDs; a repeated op is ignored. The client can retry forever without harm.
- **Coalescing:** several edits to the same record before a send are merged into one op (the last value per field). Entries are never coalesced; each is its own op.
- **No account yet?** The outbox still fills. When the person signs in later, the whole local database is uploaded as the first sync. Nothing is thrown away and nothing is replaced by an empty server account (users show: `A16#76`). The rules for merging with an existing account are in [01 §3.4](<01. Accounts and Identity.md>).

## 6. Conflicts

| Change | On two devices at once | Result |
|---|---|---|
| Habit fields (name, colour, order, …) | different fields | both kept |
| Habit fields | same field | later HLC wins |
| Entry added | both add | both kept (different IDs) |
| Same entry sent twice | — | once (same ID) |
| Edit vs delete | one edits, one deletes | delete wins; the edit is kept in the 30-day undo |
| Archive vs check-in | one archives, one logs | both kept; the entry stays in history |
| Setting (week start, day start) | same key | later HLC wins |
| Order of habits | both reorder | later HLC wins for each habit's position; ties broken by ID |

**Hybrid logical clocks** combine the device clock with a counter. A phone whose clock is set wrong can't make its old edit beat a newer one forever: the HLC always moves forward past anything it has seen. *First principles.*

**No conflict dialogs.** Every case above has a fixed answer the user can predict. The 30-day undo is the safety net, not a "choose a version" prompt.

## 7. Deletes, pause and archive

- **Delete** writes a tombstone: `(table, id, deleted_at, hlc)`. A device that later sends an older edit for that ID is ignored. So a deleted habit can never come back from an old tablet, a widget or a restored backup (users show: 13 reviews, `A1#48912`, `A23#3297`, `A13#13997`).
- Tombstones are kept for **as long as the account exists**; they are tiny. A device that has been offline for a year still can't resurrect anything. *First principles:* short tombstone lifetimes are exactly how old devices bring deleted items back.
- **Undo for 30 days:** "Recently deleted" in Settings shows deleted habits with their entries. Restoring writes a new, later record, so it syncs like any other edit.
- **Pause and archive are fields,** not deletes. They sync the same way as a name change (users show: a deactivated habit "constantly" reappearing, `P24#13064`).
- **Restoring an old backup never undoes later deletes by accident.** A restore is a merge (§8), and tombstones newer than the backup still win. If the user *wants* the old state back, the restore preview says "3 habits you deleted since then will come back" and asks (topic 3 §3.6).

## 8. Duplicates and merges

Because every record has a permanent ID, a **restore, import, re-sync or phone move is always a merge by ID**, never an append (users show: “when I restore the backup, every task gets added twice/thrice” (`A23#2573`)).

For data that arrives *without* our IDs (a CSV import, another app's export):
- A **natural key** is used: for habits, the name + type; for entries, habit + day + value + time rounded to the minute.
- Matches are shown in the import preview ("12 habits match ones you have; 3 are new"), and the user can untick them.

**If duplicates exist anyway** (from a bug, or a manual copy):
- "Merge" joins two habits: all entries move to the one kept, and the other becomes a tombstone that points to it.
- Deleting one of a pair **never** touches the other's entries. Each has its own ID, so the reported "lost both copies" (`N10#14931`, `P8#9615`) can't happen.

## 9. Health and other sources

Steps, workouts, sleep, water and mindful minutes can come from Apple Health or Health Connect.

**Decided 28 Sep 2026:**
- **Plus feature, read-only,** shipped in the first update after launch (not in v1), so it can be built and tested carefully.
- **Why Plus:** Health integration is a small but high-intent purchase reason. 1,552 reviews mention it (58 apps), and reviewers say they paid for it or would. No review resents it being paid (ledger C021: converts 1, resented 0).
- **Why careful:** broken integrations average 2.96★ (double counts, misfires, sleep on the wrong day), so the rules below matter more than shipping early.
- Evidence: [Final Backlog research](<../Research/Research Reports/Data, Sync and Accounts/QR Move, Apple Health and Launch Operations — Final Backlog.md>).

- **Read merged totals, never raw sums.** On iOS, use `HKStatisticsCollectionQuery` with cumulative sum, which merges overlapping sources the way the Health app does ([Apple docs](https://developer.apple.com/documentation/healthkit/hkstatisticscollectionquery)). On Android, use Health Connect's aggregate API ([Android docs](https://developer.android.com/health-and-fitness/health-connect/aggregate-data)). Raw samples from the phone and the Watch overlap, and summing them double counts (users show: 5 Health reviews, `A31#1210`, `N5#11064`). Confirm on real devices at build time: some developers report differences from the Health app's own totals.
- **A Health-derived day value is one entry per habit per day,** with `source = health` and `source_id` = habit + day. Each re-read replaces that entry (same ID). It never adds a new one.
- **Only one device imports.** Health data syncs between the user's own Apple devices already. If every device imported too, the same steps would arrive twice. So only the device where the user switched on the Health link imports; the others see the result through our sync. *First principles.*
- **Late data is expected.** The Watch often syncs to the phone hours later. So today and the previous two days are re-read on every launch and background refresh, and a streak can go from "missed" to "done" when data arrives (users show: “i had walk for 4 minutes before midnight and it didn’t update” (`N5#15396`)).
- **Sleep crosses midnight.** A sleep session counts for the day it *ends* (the morning), by default (users show: “The app tends to confuse about the sleep hour when retrieve data from Apple health” (`A33#2979`)).
- **Health Connect changes tokens expire after 30 days unused** ([Android docs](https://developer.android.com/health-and-fitness/health-connect/sync-data)). When that happens, re-read the last 30 days and replace by `source_id`; this is safe because the IDs are stable.
- **If we ever write to Health** (not planned), use `HKMetadataKeySyncIdentifier` + `HKMetadataKeySyncVersion` on iOS and `clientRecordId` + `clientRecordVersion` on Android, so our rewrites replace rather than duplicate ([Apple docs](https://developer.apple.com/documentation/healthkit/hkmetadatakeysyncidentifier), [Android docs](https://developer.android.com/health-and-fitness/guides/health-connect/develop/write-data)).

## 10. Widgets, Watch and shortcuts

- **One database, one write path.** *Revised in [07 Other Surfaces §3.1](<07. Other Surfaces.md>):* on iOS the SQLite file stays in the app's own container, **not** the App Group. A database in a shared container gets the app killed when it is suspended holding a lock (0xDEAD10CC). Widgets and shortcuts read a small snapshot file in the App Group. Their taps run as App Intents in the app's process, which writes the entry and its outbox row; a tap journal is the fallback. On Android, widgets run in the app's process and write through the same repository.
- **The Watch** has its own local database and syncs with our server directly when it can, and through the phone otherwise (topic 7). Its entries have their own IDs, so a check-in made on the Watch and relayed by the phone is still one entry (users show: `A53#1105`).
- **Widgets reload after every write,** from any source, including sync. A deleted habit disappears from widgets at once (users show: “I deleted the Dry January task but the widget still shows it” (`A46#1553`); `P84#12457`).
- **Widget numbers use the same calculation** as the app (§3.3), so they can't disagree.

## 11. When sync runs, and showing it

### 11.1 Triggers

| When | What |
|---|---|
| A change is made | send after 3 s of quiet |
| The app opens or comes to the foreground | pull, then send |
| Pull to refresh on Today | pull and send now |
| Network comes back | send the outbox |
| Background (iOS `BGAppRefreshTask`, Android WorkManager periodic, 15 min minimum) | best effort; not relied on |
| Another device changed something | a silent push asks the app to pull |

**Silent pushes are hints, not guarantees.** Apple throttles background notifications and advises sending no more than two or three per hour; they are never delivered to an app the user has force-quit ([Apple docs](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app)). On Android, FCM data messages are likewise deprioritised when overused. So the server sends at most one push per device per 15 minutes, and the pull on open is what actually keeps devices in step. *Platform rule.*

**Target:** a change on one device shows on another open device within about 10 seconds, and on any device the moment it's opened (users show: “it might take an hour or more for the change to appear on my iPad Pro with the devices sitting next to each other” (`A13#12937`)). An open app pulls every 60 seconds while in the foreground as a fallback to push.

### 11.2 What the user sees

- **Settings → Account & backup:** "Synced 2 min ago · 3 devices", and a **Sync now** button.
- **Today:** nothing when everything is fine. A small "Offline · saved on this phone" note when changes are waiting and there's no network. A "Couldn't sync — tap to retry" note after 3 failed attempts over 10 minutes.
- **Never "synced" when it isn't.** The time shown is the last server acknowledgement, not the last attempt (users show: `A23#4431`).
- **Offline is normal, not an error.** Nothing in the app shows a warning on items created offline (users show: `P8#1500`).

## 12. Schema versions and mixed app versions

People run different app versions on different devices, often for months.
- Every op carries the `schema` version that wrote it. Fields a device doesn't know are **kept and passed on**, never dropped. So an old iPad can't erase a field that the new iPhone added.
- New fields are always optional, with a default. A field is never renamed or re-purposed; a new one is added instead.
- If an op needs a newer schema to be understood (for example, a new habit type), the old device stores it, shows "Update the app to see this habit" in its place, and never edits it.
- The server rejects nothing because of version; it stores what it is sent. Topic 8 covers local database migrations and rollback.

## 13. Test checklist

- Two devices offline; both edit the same habit's name and colour; both come online → both changes kept.
- Two devices each log a glass of water at the same second → 2.
- The same op sent 5 times (retries, app killed mid-send) → counted once.
- Delete a habit on the phone; an iPad offline for 400 days comes online with an edit to it → stays deleted.
- Restore a backup from last month after deleting 2 habits since → the preview warns; default keeps them deleted.
- Change a habit from 3 to 5 days a week → every past week's result is unchanged.
- Log a run at 23:30 in London; fly to New York → it still shows on the same date on every device.
- Day ends at 03:00; tap at 02:30 → counts for the previous day; the Today title says so.
- Week start = Saturday → week view, week targets, charts, widgets and CSV export all group Saturday–Friday.
- DST change night → reminders fire at the same wall-clock time.
- iPhone + Watch both record steps → the day's total matches the Health app.
- Health Connect token unused for 31 days → a full 30-day re-read with no duplicates.
- Tick from a widget with the app closed → appears on another device within about 10 s after the widget's sync request.
- Force-quit the app on the second device → it catches up the moment it's opened.
- Two versions of the app on two devices, with the newer one adding a field → the older one keeps the field.
- Clock set a year ahead on one device, then corrected → no edit from it beats a later real edit (HLC).
