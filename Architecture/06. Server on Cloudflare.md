# 06. Server on Cloudflare

*Written by Claude (Claude Code), 26 Sep 2026. Topic 6 of the [architecture list](README.md). A proposal, not yet built.*

**Scope:** the production detail of our server. It covers:
- its parts and endpoints;
- what is stored where;
- how requests are checked;
- behaviour under outages and limits;
- deploys without downtime;
- backups and restoring one account;
- monitoring;
- security;
- what happens if we ever shut down.

**Already decided:** the shape (Worker + one SQLite Durable Object per account + R2), the cost model, the free-plan launch and the exit plan are in [Data Safety, Accounts and Sync §3.3, §3.4 and §7](<Data Safety, Accounts and Sync.md>). The sync protocol is in [05 Sync Engine](<05. Sync Engine.md>). This doc does not repeat them.

**How each rule is backed:**
- **Users show**: backed by review evidence.
- **Platform rule**: a Cloudflare limit or behaviour, with a link.
- **First principles**: reasoned from how the system works.

**Evidence:**
- **A fresh screen:** 1,487,223 reviews, 8 server patterns (outages, online-only, loading, shutdown, breach, maintenance, recovery), 1,928 matches.
- **171 read in full and coded,** with quotes verified. 95 are about this topic (the words "shut down" and "maintenance" catch many unrelated reviews).
- **Files:** [`Server Evidence/`](<../Research/Research Reports/Data, Sync and Accounts/Server Evidence/>).

## 1. The design on one page

1. **The server is never in the way.** Nothing the user does waits for it: not opening the app, not ticking a habit, not creating one, not even signing up. If the server is down, the app works exactly the same and says "Saved on this phone" (users show: outages that made "all of my *daily* habit tracking inaccessible").
2. **Four parts, one domain.** A Worker at `api.<ourapp>.com`, one Durable Object per account, one small D1 directory, and R2 for snapshots and phone moves.
3. **Every request is checked at the edge** (our session token, a per-account rate limit) before it can reach an account's data.
4. **No maintenance windows, ever.** Deploys are gradual and data changes are applied per account, lazily, as each one next syncs (users show: “They don’t announce maintenance or server outages” (`A85#67`)).
5. **Honest errors.** A server fault is never reported as "check your internet connection", and a failed save is never shown as saved (users show: `A85#102`, `A68#4348`).
6. **Three backups we can restore one account from:** 30-day point-in-time recovery, nightly R2 snapshots, and a weekly copy outside Cloudflare. We practise a restore every month.
7. **We know before users do.** An outside health check, a daily usage email, error-rate alerts, and the data-loss canary (topic 8).
8. **We store as little as possible.** No passwords, hashed tokens, no health details beyond what sync needs, and deletion that really deletes (users show: spam "that contain all my data" after deleting an account).
9. **If we ever shut down, nobody loses anything.** The app keeps working offline for good, and a final update removes every server dependency (users show: 5 shutdown reviews).

## 3. The parts

```
 phone / tablet / watch / web
            │  HTTPS, api.<ourapp>.com
            ▼
 ┌─────────────────────────── Worker "api" ───────────────────────────┐
 │ checks token · rate limit · routes · verifies Apple/Google tokens  │
 └────┬─────────────────────┬──────────────────────┬──────────────────┘
      ▼                     ▼                      ▼
 Durable Object       D1 "directory"          R2 buckets
 "Account" (1 each)   sign-in key → account   snapshots/ · moves/
 SQLite: records,     (written at sign-up)    (nightly · 15-min QR slots)
 ops, devices,
 entitlements
      ▲
 Cron Worker (daily): usage report · snapshots · off-Cloudflare copy (weekly)
```

| Part | Holds | Why this one |
|---|---|---|
| **Worker `api`** | nothing | Stateless routing and checks. Free plan: 100,000 requests a day and 10 ms of CPU per request ([limits](https://developers.cloudflare.com/workers/platform/limits/)) |
| **Durable Object `Account`** | everything for one account | Writes happen one at a time, so there are no races. Up to 10 GB per object ([limits](https://developers.cloudflare.com/durable-objects/platform/limits/)); an account is about 0.2 MB a year |
| **D1 `directory`** | Apple `sub` / Google `sub` → account ID; account created date | The only lookup that has to work across accounts. Tiny, and written only at sign-up and linking |
| **R2** | nightly snapshots; QR-move slots (topic 4) | Cheap object storage with no egress fee |
| **Cron Worker** | nothing | Daily jobs. The free plan allows 5 cron triggers |

**Endpoints** (all JSON, all versioned under `/v1`):

| Endpoint | Does | Topic |
|---|---|---|
| `POST /v1/sync` | push outbox, pull changes | 05 |
| `POST /v1/auth/apple`, `/v1/auth/google` | exchange a provider token for our session | 01 |
| `POST /v1/auth/refresh` | rotate the refresh token | 01 |
| `POST /v1/account/link`, `/v1/account/delete`, `GET /v1/account/export` | linking, deletion, export | 01, 09 |
| `POST /v1/purchases/verify` | verify a store purchase | 02 |
| `POST /v1/hooks/apple`, `/v1/hooks/apple-id`, `/v1/hooks/play` | App Store notifications, Sign in with Apple notifications, Play RTDN | 01, 02 |
| `POST /v1/move`, `GET /v1/move/{id}` | QR phone move slot | 04 |
| `GET /v1/status` | "is sync working?" (no auth, cached 30 s) | this doc |

**One more rule:** everything Cloudflare-specific sits behind a small `Store` interface (`getAccount`, `applyOps`, `changesSince`, `snapshot`). The exit plan's plain server implements the same interface.

### The one email

The only email is the purchase confirmation (decided 27 Sep 2026; topic 1 §3.8). It is sent through a server-side sender interface after a verified Plus or Plus Family purchase, and only to an account's Apple or Google email. The job is committed with the verified purchase, sent at most once, and never blocks the entitlement. Provider credentials are backend secrets. An external sender runs on Workers Free. See [Email Delivery Decision](<Email Delivery Decision.md>).

## 4. The Account Durable Object

One object per account, named by account ID. Its SQLite database holds:

| Table | Holds |
|---|---|
| Record tables (`habit`, `habit_rule`, `entry`, `section`, `setting`, `tombstone`) | the same schema as the phone (topic 5) |
| `op_log` | every applied op: seq (increasing), op ID, device, HLC, fields |
| `device` | device ID, name, platform, app version, last seen, push token |
| `session` | hashed refresh tokens, per device |
| `entitlement` | verified purchases and their state (topic 2) |
| `email_delivery` | the purchase confirmation job: unique message key, attempts and provider result; committed with the purchase and cancelled on deletion |
| `meta` | schema version, created, last snapshot |

**A sync request, step by step:**
1. The Worker checks the access token and sends the request to the account's object.
2. The object applies the schema upgrade if its `meta.schema` is behind (§8).
3. In **one transaction**: skip ops whose ID is already in `op_log`; merge the rest field by field (HLC); append them to `op_log`.
4. Read everything with `seq` greater than the device's cursor, excluding the device's own ops, up to 1,000 ops.
5. Reply with those changes, the new cursor, and "more: true" if there are more.

The merge/validation rules in step 3 come from the shared KMP core compiled with Kotlin/JS; the Worker/Durable Object adapter owns authorization, storage and the transaction. Verify the exported module in the Cloudflare runtime during implementation. See [Shared Core Decision](<Shared Core Decision.md>).

The client only marks its outbox rows as sent after step 5 returns (topic 5). A crash anywhere before that is harmless, because the retry is ignored as a duplicate.

**Compaction:** `op_log` rows older than 90 days, and already seen by every active device, are dropped; the record tables still hold the current state. A device that has been away longer than that gets a full copy instead of a delta. Tombstones are never compacted (topic 5 §7).

**Limits that matter:**
- One object handles about 1,000 requests a second ([limits](https://developers.cloudflare.com/durable-objects/platform/limits/)). One person's devices send a few a minute.
- Row size is capped at 2 MB and a SQL statement at 100 KB. A push is therefore capped at 500 ops; a bigger outbox is sent in chunks.

## 5. Checking requests

- **Sign-in:** the Worker checks the Apple or Google ID token's signature against the provider's published keys (cached for an hour), plus its audience, issuer and expiry. Then it looks up or creates the account in D1 (topic 1).
- **Our tokens:**
  - an **access token** lasting 1 hour: a signed token with account ID and device ID, checked in the Worker with no database read;
  - a **refresh token** that rotates on every use, stored only as a hash in the account's `session` table.
  - A reused old refresh token signs that device out (a theft signal); other devices are unaffected.
- **Never expire a session for inactivity** (topic 1). A person who comes back after a year is still signed in.
- **Premium is never removed by a failed check.** If store verification fails or times out, the last verified state stands and we retry. Only a store notification (refund, expiry) changes it (users show: `P98#770`; topic 2's "never downgrade on doubt").
- **Store webhooks** are checked too: Apple's signed payload against Apple's root certificate, and Play's Pub/Sub push against its token. They are idempotent by notification ID.

## 6. Limits, rate limiting and back-off

**The free plan's daily limit:** 100,000 Worker requests a day, resetting at **midnight UTC**. Past it, Cloudflare returns error 1027 ([limits](https://developers.cloudflare.com/workers/platform/limits/)). We choose "fail closed", so requests get that error rather than reaching nothing. The app treats 1027 like any outage: it keeps the outbox and tries again later.

**Rate limiting per account:** the Workers rate-limiting binding, keyed by account ID (not IP, which many mobile users share). Budget: 60 syncs a minute per account. Its counts are per location and approximate ([docs](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)); it is a guard against runaway loops, not billing. Unauthenticated routes (`/auth/*`, `/move`) are limited by IP with a looser budget, plus a Cloudflare WAF rate rule so floods never count against the daily limit.

**Client back-off:**
- On a 429, a 5xx, 1027 or a network error: wait and retry with exponential back-off (2 s, 4 s, 8 s … up to 15 min) plus random jitter, so a million phones don't retry in the same second after an outage.
- Honour `Retry-After` when the server sends it.
- The server can reply `{"slowDown": 300}` to stretch every client's interval during an incident.
- Foreground and pull-to-refresh reset the back-off once, so a user who asks gets one immediate try.

## 7. When the server is down or slow

The app's behaviour, by case:

| Case | User sees | Behind the scenes |
|---|---|---|
| Server down | nothing on Today; "Saved on this phone" in Settings | outbox holds changes; back-off retries |
| Server slow | nothing | sync runs in the background with a 20 s timeout; no screen waits for it |
| Sign-up fails | "Couldn't reach our server. You can keep using the app; we'll finish signing you in later." | the app retries in the background; no data depends on the account existing |
| Purchase can't be verified | Plus is unlocked from the store's own receipt on the device | server verification retried; topic 2 |
| Sync failing for over 24 h | a quiet note: "Backup to your account paused since yesterday. Your data is safe on this phone." | alert already sent to us |

**No launch-time network calls** block the first screen. The app opens from local SQLite and syncs after the first frame (users show: 17 slow-start reviews; `P5#868`).

**Error wording:** our fault is "Our server is having trouble"; the network is "You're offline". Never mixed up (users show: `A85#102`). Errors are shown once, not repeatedly (users show: `N7#9882`).

**`/v1/status`** feeds a status line in Settings and a public status page, so support can point to it.

## 8. Deploys and data changes without downtime

- **Two environments:** `staging` and `production`, separate Cloudflare accounts, separate domains. TestFlight and internal-track builds talk to staging.
- **Worker deploys are gradual:** 5% → 25% → 100%, over at least an hour, watching error rates. Cloudflare supports this and rollbacks to a previous version ([docs](https://developers.cloudflare.com/workers/configuration/versions-and-deployments/gradual-deployments/)). **Durable Objects run only one version at a time each**, so every object-code change must work with data written by the old version. Confirm at build time how objects are assigned to versions during a gradual deploy.
- **Server schema changes are lazy and additive:**
  - each object stores its schema version and upgrades itself on its next request, in one transaction;
  - only adding tables, columns and indexes; never renaming or dropping in the same release;
  - an upgrade that fails leaves the object on the old version and alerts us. That account keeps syncing old-style until it's fixed.
- **Protocol versions:** the server accepts the current and the previous two protocol versions. An old app is never cut off; at worst it is asked to update to see new features (topic 5 §12).
- **No maintenance windows.** Nothing in this design needs one. If something ever did, users would be told a day ahead in the app, and edits would still be saved locally (users show: `P122#14960`).

## 9. Backups and restoring one account

| Copy | How far back | Cost | Protects against |
|---|---|---|---|
| Durable Object point-in-time recovery | any moment in the last **30 days** ([docs](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)) | included | our own bug, a bad deploy |
| Nightly R2 snapshot, per account changed that day | 90 days of nightlies, then monthly for a year | pennies | the above, beyond 30 days |
| Weekly export outside Cloudflare | 8 weeks | pennies | losing the Cloudflare account |
| Every user's phone | always | — | everything above |

**Restoring one account** (a support tool, never a manual database edit):
1. Pick a time, get the point-in-time bookmark, and restore into a **new** object, not the live one.
2. Compare it with the live account: habits and entry counts per habit.
3. Merge missing records into the live account as new ops. Phones then receive them through normal sync. Never overwrite the live account; newer edits from the user are kept.

**Restore drill:** once a month, restore a test account from each copy and check it. A backup nobody has restored is only a hope (users show: 9 reviews of lost or unrestorable data, mean 1.1).

## 10. Monitoring

- **Outside health check:** a free uptime monitor calls `/v1/status` every minute from outside Cloudflare, and emails and pushes to us on failure.
- **Logs:** Workers Logs, kept 3 days on the free plan and 7 on paid, with 200,000 log lines a day free ([docs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)). We log one line per request (route, status, duration, account hash), never habit content.
- **Daily cron report (email):**
  - requests, syncs and new accounts yesterday;
  - percentage of the free daily limit used (alert at 50%, the upgrade trigger);
  - error rate by route;
  - objects that failed a schema upgrade;
  - snapshot and off-Cloudflare job results.
- **Alerts:** 5xx above 1% for 5 minutes; any snapshot job failure; the data-loss canary (topic 8).
- **Cost alerts:** Cloudflare billing notifications once on the paid plan.

## 11. Security and privacy

- **No passwords, ever.** Sign-in is Apple and Google only at launch, so there is nothing to leak or store in cleartext (users show: `A24#27583`, `P24#2237`).
- **Tokens:** refresh tokens are stored hashed; access tokens are short-lived. Signing keys live in Worker secrets and are rotated yearly, with the old key still accepted for a day.
- **Store only what sync needs.** Names of habits and entries are needed to sync. We don't ask for gender, age or life goals at sign-up (users show: worry that personal answers "can be used by hackers" (`P12#30872`)).
- **Account email** is kept only for the one purchase confirmation and for support lookup. There is never any marketing. Deleting the account deletes it (users show: `A33#1119`; topic 9).
- **Encryption:** TLS in transit; Cloudflare encrypts at rest. End-to-end encryption is parked (see the main doc §3.3).
- **Our own access:** production access needs two-factor sign-in, is limited to two people, and every support restore or data view writes an audit record.
- **Logs never contain habit names, notes or tokens.**

## 12. If we ever shut down

Users worry about this even when happy (`P122#7591`). Five reviews in the sample describe an app or service that was discontinued, and people who lost one say so when they arrive (`P84#9989`).

Our promise, written in the privacy policy and on the website:
1. **At least 6 months' notice,** in the app and on our website.
2. **A final app update** that turns off sync and sign-in, keeps everything local, and keeps on-device snapshots and file export working (topic 3). The app keeps working offline for as long as the phone runs it.
3. **A full export for every account,** in the open `.habits.zip` format, downloadable until the server closes.
4. **Premium stays unlocked** in the final update for everyone who ever bought it.

Because the phone is already the source of truth, this costs almost nothing to honour. That makes it a promise we can safely make.

## 14. Test checklist

- Kill the server mid-sync (after apply, before reply) → the retry is ignored as a duplicate; nothing is doubled.
- Block the API for 3 days → the app works throughout; everything syncs within a minute of unblocking.
- Hit the free daily limit on staging → apps get 1027, keep their outbox, and catch up after midnight UTC.
- 10,000 simulated phones reconnect at once after an outage → retries spread over minutes (jitter); no second outage.
- Sign up with the server down → the app is fully usable; sign-in completes later on its own.
- Deploy an object schema change gradually → accounts upgrade on their next sync; old app versions keep syncing.
- Roll back a Worker version → no data change, no error spike.
- Restore an account to yesterday into a new object, then merge → no newer user edits lost.
- Monthly restore drill from R2 and from the off-Cloudflare copy.
- Run the full protocol test suite against the `exit/` server → it passes the same tests as Cloudflare.
- Revoke a refresh token by reusing it → only that device is signed out.
- Store verification times out → Plus stays unlocked.
