# 11. iCloud Sync with CloudKit (CKSyncEngine)

Written by Claude (Claude Code), 10 October 2026, for Current Work 81, at the user's request: "do the research,
complete the research … we need to ensure it's a robust and very reliable syncing. Consider data should be never
lost. That is the really, really most important thing … whatever the limits that we have on the cloud, take care of
all of those things, so that for extreme users … data [is never] not going to the server … because of the limits …
build a very robust system for production."

**Status:** research done; this is the design another agent builds from (Rulebook D16, decided 10 Oct 2026). It
replaces our server's sync and accounts on Apple devices. Architecture 05 (the sync engine's rules) still holds:
CloudKit replaces the *transport*, not the rules.

**Evidence:** Apple's documentation for `CKSyncEngine`, `CKError` and CloudKit encryption (read today); Apple's
sample project; a developer's production write-up (Christian Selig, Jan 2026); Apple developer-forum answers from
Apple engineers (DTS); our own code (`Core/sync`, `SyncWriter.kt`, `Records.kt`, `iOS/Habits/Backup`, `Model/SyncService.swift`);
and **44 hand-read reviews of iCloud sync failing in habit apps** (`Research/Temp/no-server/icloud_codes.py`).

---

## 1. The answer

**Yes: CloudKit's private database with `CKSyncEngine` can be made as safe as our server, and simpler, if we keep
four things that make data loss impossible by design:**

1. **The phone's own database stays the truth** (D1). iCloud is a copy. Nothing that happens in iCloud (signing out,
   a full iCloud, a deleted zone, another Apple Account) ever deletes the phone's data.
2. **Our outbox stays the record of what hasn't reached iCloud.** A change leaves the outbox only when CloudKit
   confirms it saved that exact change. The sync engine's own queue is a helper, not the truth, because it drops
   items on some errors (§7).
3. **Nothing is ever deleted through sync.** A delete is a field (`deleted_at`, the tombstone we already use), so the
   only thing sync can do to data is add or merge. A bug, an empty phone or an old device can't erase anything.
4. **A second, separate safety net:** dated backup files in iCloud Drive, never replaced by a smaller one, outside the
   sync path, so a bad state that syncs everywhere can still be undone.

**The limits are handled by design:** small records, batches built by Apple's own batcher (250 records a request),
the engine's automatic retries for throttling and network errors, our own retries for the errors it doesn't retry
(a full iCloud), and a yearly compaction for very old history so an extreme user's iCloud use stays small (§14).

**A cloud agent can build almost all of it** (§22): the code and its tests run on GitHub's simulator against a fake
iCloud that reproduces every error. Real iCloud needs the user's iPhone and a second device for the final checks.

## 2. The words

| Word | What it is |
|---|---|
| **iCloud** | What people see: the storage that comes with their Apple Account. In the app we only ever say "iCloud" |
| **CloudKit** | Apple's framework that lets our app keep data in each person's iCloud. We use its **private database**: each person's own space, which **we as developers can't read**, and which counts toward **their** iCloud storage, not ours |
| **`CKSyncEngine`** | The part of CloudKit (iOS 17+, macOS 14+, watchOS 10+; our app needs iOS 18) that runs sync: schedules sends and fetches, listens for silent pushes, retries the errors it can |
| **Zone** | A folder of records inside the private database. Sync works zone by zone |
| **Record** | One item in CloudKit, at most 1 MB of fields |

Examples: "Changed devices and lost months worth of data, even though I had iCloud sync enabled" (Productive, 2★,

## 4. Apple's facts and limits we design around

| Fact or limit | Value | Source |
|---|---|---|
| Records per send request | **250** (saves + deletes); over it fails with `limitExceeded`. `RecordZoneChangeBatch(pendingChanges:recordProvider:)` stops at the limit and leaves the rest pending | Apple, `CKSyncEngine` |
| General per-request guide | 400 items and 2 MB (assets excluded); "the server can change its limits at any time" | Apple, `CKError.limitExceeded` |
| Record size | **1 MB** of fields, assets excluded | Apple DTS (forum), CloudKit Web Services reference |
| Errors the engine retries itself | `notAuthenticated`, `accountTemporarilyUnavailable`, `networkFailure`, `networkUnavailable`, `requestRateLimited` (after its retry-after time), `serviceUnavailable`, `zoneBusy` | Apple, `CKSyncEngine` |
| Errors **we** must handle | `serverRecordChanged` (a conflict), `zoneNotFound`, `unknownItem`, **`quotaExceeded` (not retried; the item is dropped from the engine's queue)**, `limitExceeded`, `invalidArguments` | Apple; Selig |
| Scheduling | Automatic when signed in, online and in good conditions; may be delayed (low power, no network); `fetchChanges()` / `sendChanges()` to force | Apple, `CKSyncEngine` |
| State | An opaque state the app **must persist** on every `stateUpdate` event, or the engine can't resume | Apple, `CKSyncEngine` |
| Pushes | The engine creates a database subscription and listens for silent pushes: needs the **CloudKit** and **Remote notifications** entitlements | Apple, `CKSyncEngine` |
| Accounts | The engine stays dormant without an account and sends `accountChange` (signed in, signed out, switched) | Apple, `CKSyncEngine` |
| Zone deletions | Reported with a reason: deleted (by code), **purged** (the person deleted the app's iCloud data in Settings), **encryptedDataReset** (keys reset in account recovery) | Selig; Apple, `CKFetchDatabaseChangesOperation` |
| Conflicts | The engine saves with "if the server record is unchanged"; a newer server copy returns `serverRecordChanged` with the server's record. The app must keep each record's **system fields** (`encodeSystemFields`) or every save conflicts | Apple DTS; Selig |
| Deletes | Skip conflict resolution: "will trust you know what you're doing and just delete it" | Selig |
| Encrypted fields (`encryptedValues`) | End-to-end; if the person's iCloud Keychain is reset, the data "becomes permanently lost" and the zone is removed | Apple, Encrypting user data |
| Production schema | TestFlight and App Store builds use the **Production** environment; the schema must be deployed there first; fields and types can never be removed from Production | Apple DTS (forum) |
| Public database | Not supported by `CKSyncEngine`; we never use it | Apple |
| One engine per database | Don't run two engines on one private database | Selig |

## 5. The design at a glance

```
 Phone (the truth)                                   The person's iCloud
 ┌──────────────────────────────┐                    ┌───────────────────────────────┐
 │ SQLite (Room, shared core)    │                    │ CloudKit private database      │
 │  habit, step, reminder,       │   CKSyncEngine     │  zone "Habits": one record per │
 │  entry, setting               │ ◀───────────────▶ │  row (fields + clocks, JSON)    │
 │  sync_meta (clocks, CK system │  250 a request,     │  zone "Control": the free plan's│
 │  fields), outbox, local_state │  retries, pushes    │  syncing device, device list   │
 │  (engine state)               │                    ├───────────────────────────────┤
 └──────────────┬────────────────┘                    │ iCloud Drive (app container)    │
                │ daily, never smaller                 │  dated backup files (§13)       │
                └────────────────────────────────────▶└───────────────────────────────┘
```

- **Shared core (Kotlin) keeps the rules:** `SyncWriter` (every change → an op → merged → outbox), `SyncRules` (merge
  field by field, delete wins, unknown fields kept), `SyncCodec`. One addition: `SyncRules.mergeRecord` (a whole
  record with per-field clocks, as CloudKit returns it; equivalent to applying one op per clock).
- **New Swift layer `CloudSync`:** owns the one `CKSyncEngine`, turns outbox rows into CloudKit records and fetched
  records into merges, stores the engine's state, and reports a status. Behind a protocol (`CloudTransport`) so tests
  use a fake iCloud (§21).
- **Plus** comes from StoreKit (the Plus screens work), never from iCloud.

## 6. The data layout in CloudKit

**One custom zone, `Habits`, in the private database** (custom zones give change tracking and atomic saves; the
default zone doesn't). A second small zone, **`Control`**, for the free plan's syncing device and the device list
(§12).

**One record type, `Row`, for every table**, with fixed fields that never change:

| Field | Type | Holds |
|---|---|---|
| `table` | String | `habit`, `step`, `reminder`, `entry`, `setting` |
| `row` | String | The row's permanent ID (UUIDv7, made on the device) |
| `fields` | String (JSON) | Every field of the row, including fields this app version doesn't know (05 §12) |
| `clocks` | String (JSON) | Each field's hybrid-logical-clock stamp |
| `schema` | Int64 | The app schema that wrote it |
| `format` | Int64 | This layout's version (1) |

- **Record name:** `<table>:<row>` (for example `entry:0192f…`). Stable forever, so a row has exactly one record and a
  restore or a second copy can never duplicate it.
- **Why one generic type with JSON:** the CloudKit schema is set once and **never changes**. New app fields need no
  CloudKit schema deploy, so the classic production failure ("works in Xcode, fails in TestFlight" because a field
  wasn't deployed) can't happen, and older app versions keep newer fields untouched (they're just JSON). We never
  query CloudKit; we only sync, so we lose nothing by not having typed fields.
- **Deletes are never CloudKit deletions.** A deleted habit or log is a `Row` whose `fields` has `deleted_at`, exactly
  the tombstone 05 §7 keeps for ever. So the engine's "deletes skip conflict resolution" never applies to people's
  data, an old device can't resurrect anything, and nothing depends on how long CloudKit remembers deletions.
  CloudKit deletion is used only for "Delete my data from iCloud" (§17), and for compaction (§14), both deliberate.
- **Local settings stay local** (`SyncCodec.isLocalSetting`), as today.
- **Size guard:** a row is a few hundred bytes; notes are capped by `TextLimit` in the app. Before sending, a record
  over **256 KB** is refused locally and logged (it can never fail at CloudKit's 1 MB).
- **System fields:** `sync_meta` gains a column `ck_system` (the record's encoded system fields, a few hundred bytes).
  A Room migration adds it (D2: tested from every past version, a copy kept first, never reset on error).

## 7. Sending: from the outbox to iCloud

1. A change is written with its op to the outbox **in the same transaction** (as today). `CloudSync` adds the row's
   record name to the engine's pending saves (`state.add(pendingRecordZoneChanges: [.saveRecord(id)])`).
2. **`nextRecordZoneChangeBatch`** builds the batch with Apple's `RecordZoneChangeBatch(pendingChanges:recordProvider:)`
   (it stops at the request limit). For each record it uses the stored system fields (or a new record), fills the six
   fields from the row's **current merged state**, and remembers the newest clock it included.
3. **On `sentRecordZoneChanges`:**
   - **Saved:** store the returned system fields; delete from the outbox **only** that row's ops whose clock is ≤
     the newest clock that was sent. A change made while the batch was in flight stays queued.
   - **Failed**, by error:

| Error | What we do |
|---|---|
| `serverRecordChanged` | Merge the server's record into the row (`mergeRecord`), store its system fields, queue the row again. The merge is commutative, so both devices converge |
| `zoneNotFound` | Queue a zone save, then the row again. If the zone was **purged** by the person, see §11 first |
| `unknownItem` | Clear the stored system fields and queue the row again as a new record |
| `quotaExceeded` (iCloud full) | **Keep the outbox.** Mark the status "iCloud is full"; stop re-queuing until the account or storage changes, the app opens, or a day passes; then re-add every outbox row (the engine dropped them) |
| `limitExceeded` | Shouldn't happen with Apple's batcher; if it does, re-queue the rows and halve our own cap for this run |
| `invalidArguments`, or a record we refused (§6) | Keep it in the outbox with `problem` set (the existing column), report it, never retry forever, never drop silently |
| Anything else | Keep the outbox; log content-free telemetry; re-queue on the next launch |

4. **On every launch** (and after an account comes back), `CloudSync` re-adds a pending save for every row that has
   outbox ops. The engine's own queue may have lost items (quota, a crash, a lost state); the outbox can't.
5. **Never a lost change:** a change leaves the outbox only on a confirmed save of a record that contains it.

## 8. Fetching: from iCloud to the phone

- **`fetchedRecordZoneChanges`:** for each modified `Row`, decode and merge it with `mergeRecord`, store its system
  fields, and write everything in **one database transaction before the handler returns**. The engine then saves its
  new state; if the app dies in between, the same changes come again and the merge ignores what's already applied
  (it's idempotent). The other order (state saved, changes not applied) can't happen because we apply first.
- **A record that can't be decoded** (a future format, damage): keep it aside in `sync_meta.extra` / a quarantine
  table with its raw JSON, never overwrite the row with it, report it. A newer app version applies it later.
- **Deletions of records** (only ever from compaction or a deliberate zone deletion): never delete a local row
  because a record disappeared; the row's tombstone field is what deletes.
- **Big first fetch** (a new device, an extreme account): applied page by page, each page its own transaction, with
  progress shown ("Bringing your habits from iCloud: 12,000 of 380,000"). The app stays usable.
- **`fetchChanges()` on coming to the foreground**, since pushes aren't guaranteed (the engine also fetches on its
  own schedule).

## 9. The engine's state

- Saved on every `stateUpdate` into `local_state` (the same SQLite file), so the app's data and the engine's position
  are backed up and restored together.
- **If the state is lost or unreadable,** start a new engine with no state: it fetches everything again (merges are
  idempotent) and the outbox re-queues everything unsent (§7.4). Slow, never lossy.

## 10. iCloud account changes: never delete the phone's data

Apple's sample deletes local data on sign-out and on a switch of account. **We don't**, ever (D1):

| Event | What we do | What the person sees |
|---|---|---|
| Signed out of iCloud, or iCloud turned off for the app, or no account | Stop syncing; keep everything; the outbox keeps growing | "Not backed up to iCloud: iCloud is off. Your habits are on this iPhone." with Turn On (opens Settings) and Export |
| Signed back in to **the same** Apple Account (we keep a hash of the CloudKit user record ID) | Resume; re-queue the outbox; fetch | Nothing special |
| **A different** Apple Account | **Ask first**, showing what's where: "This iPhone now uses a different Apple Account. Its iCloud has 0 habits / 14 habits." Keep on This iPhone Only · Add to This Account's iCloud (a merge by ID, like D3) | The choice, never a silent upload or wipe |
| Account temporarily unavailable or restricted (Screen Time, managed) | Wait; status says why | "iCloud isn't available on this iPhone right now" |

## 11. When iCloud's copy is removed

| Reason | Who did it | What we do |
|---|---|---|
| **purged** | The person: Settings › Apple Account › iCloud › Manage Storage › Often Enough › Delete | Keep everything on the phone. Ask once: "Your habits were removed from iCloud. Back them up to iCloud again?" (Back Up Again · Not Now). Not Now stops syncing on this device until they turn it back on |
| deleted | Us, only from "Delete my data from iCloud" | Expected; local data stays unless they also chose to erase the phone |
| encryptedDataReset | Account recovery reset the keys (only matters for encrypted fields) | Re-create the zone and re-upload everything from the phone (Apple's guidance) |

## 12. Free plan: one syncing device at a time (decided)

- **Plus:** every device signed in to the Apple Account syncs.
- **Free:** one device syncs, the **active device**, recorded in `Control` as one record `activeDevice` (device ID,
  name, time, clock). Others don't run the engine at all; they read just that one record (a direct fetch) to know
  where things stand.
- **A free person opens the app on a second device** with habits in iCloud: the second-device sheet (Plus screens
  3.1): Keep Both in Sync (Plus) · Move to This iPad. Move writes `activeDevice` = this iPad (saved only if
  unchanged, so two devices can't both win), then the iPad fetches everything.
- **The handover never loses the old device's last changes:** when a device sees it's no longer active, it **first
  sends its outbox** (changes made before the handover time), then stops syncing and says so: "Your habits now sync
  on your iPad. This iPhone keeps everything it has." Its later changes stay on it (and in its own backup file).
- **Two free devices both offline**, each thinking it's active: the first to reach iCloud keeps it; the other flushes
  its earlier changes on the next fetch and stops, as above. Nothing is lost; at worst both devices' changes merge.
- **Plus ends** (a refund): the device that notices becomes the active device; the others flush and stop, with the
  message from the Plus screens (7.1).

## 13. Data-safety guards beyond sync

1. **A fresh install never treats "nothing here" as the truth.** On first launch with iCloud on, it fetches before
   offering "Start fresh", and the welcome waits for iCloud (as D4 already requires for iCloud Drive). Demo or sample
   habits are never created on a device whose iCloud has habits, and never sync in Debug builds (D14).
2. **A mass-change brake, both ways.** If a single run would tombstone more than 20% of live rows or more than 50
   rows that weren't one explicit action ("Delete these 60 logs"), sending pauses and the app asks. If fetched changes
   would tombstone more than 20% of live rows at once, applying pauses and the app asks, with "Restore From a Backup"
   one tap away. A bug can't quietly empty every copy.
3. **Dated backup files, outside sync.** The daily backup file (iCloud Drive, the app's container) becomes a set:
   the last 7 days, 4 weeks and 6 months, never replaced by a file with far fewer records (D4's never-shrink rule),
   pruned beyond a size budget (keep at least 3). Restore from any of them (D5, with its 30-day undo). These don't
   change when a delete syncs, so they can bring back what sync spread.
4. **A cloned device gets its own identity.** An iPhone restored from another's device backup carries the same sync
   node ID; when `identifierForVendor` differs from the one stored with the node, a new node ID is made, so two
   devices never share clock stamps.
5. **Export stays one tap away and free** (D10), as a file anyone can keep.

## 14. The extreme user and every limit

Assumptions from the price work: 60 habits, about 70 logs a day (25,000 records a year), 3 devices, 15–20 years.

| Limit | Extreme load | How it's handled |
|---|---|---|
| 250 records a request | ~70–100 changes a day, sent in seconds-apart batches | Apple's batcher; a day of changes fits in one request |
| Rate limits (Apple doesn't publish them) | First upload of 15 years: ~375,000 records ≈ 1,500 requests | The engine waits the retry-after time and continues; the state is saved, so it resumes after quits and restarts; progress shown; daily use isn't blocked |
| 1 MB a record | A row is ~300–600 bytes | Our 256 KB guard (§6) |
| The person's iCloud storage | 375,000 records: estimated 200–400 MB including CloudKit's own per-record overhead (to measure) | **Yearly compaction** (below) brings years older than 2 to ~2–3 MB a year |
| Big first fetch on a new device | Up to ~380,000 records | Paged, a transaction per page, progress; compaction makes it far smaller |
| Pushes not delivered | — | Fetch on foreground; the engine's own schedule |
| Long offline (months) | Change token expiry | The engine refetches; merges are idempotent; tombstones are records, so no deletion is missed |

**Yearly compaction (phase 2, designed now, built before any account is two years old):** for each habit and each
year older than two, one `Archive` record holds that year's entries as a compressed file (a `CKAsset`, about 89
bytes a record as our backup measures), with their clocks. The device that writes the archive saves it, waits until
it's confirmed, then deletes those entries' individual records. A device that later edits an archived entry simply
saves that entry as an individual record again; on reading, an individual record and the archive merge by clocks
like anything else. Two devices writing the same archive merge it (union by ID). So compaction can never lose a log.

## 15. Changes made outside the app

Widgets, notification buttons and the Live Activity save through the app (U26, D12). After such a save, `CloudSync`
calls `sendChanges()` inside `beginBackgroundTask`, so the change reaches iCloud without the app being opened. All
of it keeps `authenticationPolicy = .alwaysAllowed` and works on a locked iPhone (D13). The widget code itself is
locked (U28) and doesn't change: only what happens after the app has saved.

## 16. Encryption

**Decided by the user, 10 Oct 2026: no `encryptedValues`** ("if we don't set encryption … will it help in any kind
of recovery in the most critical times, then let's not set it"). It does help: Apple's documentation is clear that encrypted fields are
"permanently lost" if the person's iCloud Keychain is reset in account recovery; with the phone lost too, the habits
would be gone. Without them, the data is still protected by Apple's standard iCloud encryption, and **we can't read
anyone's private database** in any case, so "we never see your habits" stays true. Encrypted fields can be added
later for new records if ever wanted (CloudKit can't encrypt a field that already exists, so it would be a new field).

**Why it helps recovery:** the worst case is someone who loses every Apple device and goes through Apple's account
recovery. Account recovery can reset the iCloud Keychain; data in encrypted fields can then never be read again, and
CloudKit removes it. Data in ordinary fields is readable again as soon as they're back in their Apple Account, so a
new iPhone gets every habit from iCloud. People who turn on Apple's Advanced Data Protection choose stronger
protection for their whole account themselves; that's their setting, not ours.

## 19. How it's tested

**On GitHub (the cloud agent):**

- **A fake iCloud** (`FakeCloud`, behind `CloudTransport`) that keeps zones and records in memory and can be told to:
  conflict (`serverRecordChanged`) on chosen records; enforce 250 a request; return `quotaExceeded` until space
  frees; throttle with retry-after; lose the network mid-batch; return `zoneNotFound`, `unknownItem`, a purged zone,
  an encrypted-data reset; switch or sign out the account; deliver fetched changes twice or out of order; crash the
  app between apply and state save; lose the engine state.
- **Unit tests** (Swift, with `FakeCloud`): two and three simulated devices converge after random interleavings of
  edits, deletes and conflicts (a property test, thousands of runs); the outbox only shrinks on confirmed saves; no
  local row is ever removed by a fetch, an account change or a zone deletion; the mass-change brake trips; the free
  handover flushes the old device first; an extreme account (25,000 records a year × 15 years, generated) uploads and
  fetches within time and memory budgets; compaction never loses an entry.
- **Shared core tests** (`./gradlew jvmTest`): `mergeRecord` equals applying per-clock ops; commutative, associative,
  idempotent.
- **Migration test** (D2): `sync_meta.ck_system` added from every past schema.
- **UI tests:** the iCloud page in each status (driven by `FakeCloud` via a test launch argument), the second-device
  sheet, iCloud full, iCloud off, a different account; the SE (T15).
- **Speed** (S2, T4): a `PerfDriver` scenario for the iCloud page and for Today while a big fetch is applied.

**On the user's devices** (a local session drives the builds; the user watches):

1. Two devices, same Apple Account: log on one, see it on the other within seconds; airplane mode on both, change
   the same habit on each, reconnect: both show the merged result.
2. Delete a habit on one; the other's old offline edit doesn't bring it back.
3. Reinstall on one device: everything comes back; nothing doubled.
4. Settings › iCloud › delete the app's data: the phone keeps everything and asks to back up again.
5. Sign out of iCloud and back in; switch to a second Apple Account: nothing deleted, the question asked.
6. Free plan: Move to This iPad with unsent changes on the iPhone: they arrive on the iPad.
7. A generated extreme account on the device: first upload completes across app restarts; a new device fetches it.
8. Widgets and notification buttons on a locked iPhone: the change reaches the other device without opening the app.

## 20. Acceptance: when it's done

- Every row of §3's guard column and §7's error table has a test that fails without the guard.
- The fake-iCloud property test converges in every run; no change is lost in any injected failure.
- The device checks in §19 pass on the user's iPhone and a second device.
- The schema is in Production before the first TestFlight build.
- The iCloud page shows a true status in every state; there's no silent failure path.

## 21. Build order

1. **Groundwork:** `CloudTransport` + `FakeCloud`; `SyncRules.mergeRecord`; the `ck_system` migration; `CloudSync`
   with the engine, state saving, sending and fetching (§6–9); unit and property tests.
2. **Accounts, zones and the free plan:** §10–12, with their tests.
3. **Safety:** §13 (fresh install, brake, dated backups, clone check) and §15.
4. **The iCloud page** and the ≡ row; remove the code in §17; UI tests.
5. **Device checks** (§19) with the user; schema to Production.
6. **Phase 2, compaction** (§14), before any account is two years old.

## 22. Can a cloud agent build it?

**Yes, steps 1–4 and 6**: Swift and Kotlin code, the fake iCloud, unit, property, migration and UI tests, all run on
GitHub's simulator (T1; T17 on Linux before pushing). **What it can't do:** reach real iCloud (GitHub's simulator
can't sign in to an Apple Account), register entitlements (automatic signing on the Mac does that), or deploy the
schema to Production. So step 5 is done with the user on the Mac and their devices, in a local session.

## 23. Decided by the user (10 Oct 2026)

1. **No encrypted fields** (§16): ordinary fields can be recovered after an account recovery; encrypted ones can't.
2. **Google Drive backup on iPhone stays** for people who keep iCloud off, as built today; nothing new is built for it now.
3. **The server folder** is tagged `server-final-2026-10` and removed from `main` after CloudKit sync ships and passes
   the device checks, not before.
4. **The mass-change brake:** pause and ask when one run would delete more than **20%** of the habits and records, or
   more than **50 rows** that weren't one explicit action (§13.2).
