# The Rulebook

Written by Claude (Claude Code), 3 October 2026, at the user's request: "Everything should be in one place, so that
every agent reads it before implementing anything and avoids the same repeating mistakes."

**Every agent (Claude, Codex or any other) reads this whole file before changing anything in this repository.** It
takes about ten minutes. To point an agent here, say **"read the Rulebook"** or **"follow the Rulebook"**; to point at
one rule, use its number ("that breaks S5").

How it works:

- **Every rule that applies to any change is here, and only here.** Each one exists because a mistake was made once
  and cost something. The *why* (measurements, reviews, incidents) is in the evidence linked at the end of each
  section; read it when a reason is unclear or before arguing for a change.
- **Rule groups:** **S** speed · **D** data safety · **U** design and behaviour · **T** testing · **W** how we work.
- **Widgets are locked (U28):** read [Widgets — Taps and Updates (Locked)](<iOS/Docs/Widgets — Taps and Updates (Locked).md>) before changing anything a widget does.
- **Decisions about one screen** (what it shows, its copy, its layout) are in
  [Design Rules — Don't Regress](<iOS/Design Rules — Don't Regress.md>), one section per screen, and in that screen's
  spec ([iOS/Docs index](<iOS/Docs/README.md>)). Before changing a screen, read its section there too (U12).
- **A rule changes only here,** with the date and the reason. A product rule changes only with the user's say-so.
- **Learned something new** (a mistake, a measurement, a near miss)? Add or sharpen the rule here **the same day**,
  and put the numbers in the evidence file.

## Before a piece of work is done: the checklist

1. `iOS/Tools/perf/check_rules.sh` passes (a second, works on Linux; run it before every push). Never loosen it.
2. The tests for what changed have run and passed, **once, at the end of the piece of work** (T7). A screen or
   `HabitStore` change also gets a speed run (S2).
3. Anything that stores, sends, deletes or moves data meets every D rule.
4. A visual or layout change has been looked at on the real iPhone before it's called done (U9).
5. What you learned is written down: rules here, numbers in the evidence, the user's points ticked in their checklist.

## S — Speed (top priority: a change that makes the app slower is not finished, however it looks)

**Targets** (GitHub's simulator, a year of history): hitch time under **5 ms/s** while scrolling, tapping or typing;
**no freeze of 100 ms** or more; **opening a screen adds under 50 ms** to a blank page pushed the same way in the same
run (the hosted simulator's push alone is 120–200 ms; the iPhone 16's 45–85 ms). **The phone has the final word.**

| # | Rule | The mistake behind it |
|---|---|---|
| S1 | **The phone build is optimised.** The user installs *Debug* from Xcode, so Debug keeps `SWIFT_OPTIMIZATION_LEVEL = -O` and `KOTLIN_FRAMEWORK_BUILD_TYPE = release` | Every screen ran several times slower unoptimised (L1) |
| S2 | **Measure; never judge speed by eye, screenshots or reasoning.** Speed runs (`[ios-perf]`): the app drives itself (`PerfDriver`, a scenario per screen and interaction, handled with `.onPerfCommand`), records its own stalls (`MainThreadMeter`) and times suspect work (`perfTimed`, the "Timed work" table). Never measure through XCUITest. Typing goes through the focused field's `insertText`/`deleteBackward`, never by replacing the Binding | Screenshots and XCUITest showed freezes that weren't there and hid real ones (L2, L3) |
| S3 | **Only the smallest view that shows the time ticks** (a running row's clock, the timer bar, the player's clock). Never a `TimelineView`, `Timer` or ticking `@State` around a screen or list, not even once a minute: keep the time in `@State` and move it with a `.task` that sleeps until the next moment that matters | Today redrew every row every second; a once-a-minute ticker made scrolling 55 % busy (L4) |
| S4 | **A `TimelineView` is anchored at a fixed date**, never `.now` or `.distantPast`, and a view never switches between a `TimelineView` and a plain view (pause = a schedule that never ticks) | The app froze; the player's circle faded on Pause (L5) |
| S5 | **Anything that walks days or history is worked out once in `HabitStore` and remembered** (`streak`, `bestStreak`, `daySummary`, `placements`); never in a view's `body`. Read one habit's entries (`entries(of:)`), never every entry. Change entries only with `insertEntry` / `removeEntry(at:)` / `replaceEntry(_:at:)`. Keep the coalesced `entries` notification (one per main-actor turn) and the in-place `_modify` accessor | One tap recalculated every row's streak over a year (L6) |
| S6 | **Keep what a redraw touches small.** State that changes while scrolling lives in its own small `@Observable` read only by the view that needs it. A value read by every row is read in the smallest view that uses it. A covered screen stops drawing and its clocks pause. Stable view identities: never `.id(UUID())` | Each row's appearance rebuilt Today; Today redrew behind the player and under menu pages (L9, L15, L16) |
| S7 | **A tap changes the screen at once; the database write follows** (`addLogged`, `removeLogged`, `toggleTimer`). On a failed write, reload and say so. Never make a tap wait for storage. **A reload never hides a tap shown but not yet written:** a reload with writes queued behind it reloads again after the last of them (`reloadAfterSync`), and data is shown only once it's saved (`seedDemo`) (8 Oct 2026). **A write that waits finds its record again by ID when it runs, never by an index found before it** (Android `HabitStore.update`, 18 Oct 2026: a reorder while the write waited put another habit at that index; Arrange showed one habit twice and lost another) | Quick taps landed on the old state (L14); a ▶ tapped as the demo data appeared was wiped by its reload (TimerUITests, run 37763470033) |
| S8 | **`body` stays cheap:** no sorting or filtering of history, no `Calendar` arithmetic in loops (`LocalDay.adding(days:)`, `weekday`), no formatter or big string built per row (make it once and keep it) | A `NumberFormatter` per number was most of a row's time (L7) |
| S9 | **In a `List` with a selection, use `NavigationLink { Page() } label: { … }`**, not `NavigationLink(value:)` | The habit page never opened from All Habits |
| S10 | **Rows stay light.** A shadow only on a background shape, never on text, never a `.clear` shadow; one `.sheet(item:)` per row; no `GeometryReader` just to size a fill (`scaleEffect(x:anchor:)`); **no `ViewThatFits` in a row** (it lays out every option; choose the layout from `dynamicTypeSize` instead) | Every Today row paid an offscreen pass, four sheets and a geometry pass (L13); the after-log line's `ViewThatFits` doubled the cost of changing days (L21) |
| S11 | **Typing updates only the field.** The typed text lives in a small `@Observable` read only by the field, **and the field's binding is made in the field's own view** (`DraftTextField`, `NameField`). The form reads only "is it valid / is there a name". Anything that follows the text catches up when typing pauses (0.3 s); saving reads the live text. Never animate per keystroke | The habit form rebuilt per letter (92 % busy); the entry editor cost 24 ms/s against a bare field's 0 (L8) |
| S12 | **Charts are drawn in one pass** (`LightBarChart`, `LightLineChart`: one `Canvas`, every bar for VoiceOver, a chart descriptor for Audio Graphs). No Swift Charts in a screen that scrolls | A 1–2.7 s freeze the first time the habit page reached its chart (L10) |
| S13 | **Never a lazy grid (`LazyVGrid`/`LazyHGrid`) inside a `List` or `Form` row.** Use a plain `Grid` sized up front; lazy grids only in a `ScrollView` | Opening any habit's page crashed the app on the iPhone (L19) |
| S14 | **Ids in one lazy grid are one type** (an enum: `.weekday(i)`, `.place(i)`), and cells whose places are fixed are keyed by position, not content | Days 1–6 of every month were never drawn; cells slid on a month change (L11, L12) |
| S15 | **No `UserDefaults` write on every data change.** Write only when the value changes, or keep it in memory and save on leaving the app | The Day sheet: 535 ms/s and 36 freezes (L17) |
| S17 | **A widget timeline holds only the next few hours** (`PhoneWidgetTimeline.horizon`, 3 h) **and the next day's start; entries at least 5 minutes apart.** WidgetKit draws every entry the moment it gets a timeline, before showing anything; the snapshot's seven days carry the widget through days without the app, one short timeline at a time. No `.invalidatableContent()` on a widget's buttons (any tap dims every marked view: the rows flickered). A widget tap reloads at once, without the 250 ms coalescing. Measure widget speed on the iPhone with `WidgetLatencyDeviceTests` and the opt-in `-widget-timing on` log, never by polling the Home Screen's whole element tree (one read took ~43 s) | A week of entries (21 for a Medium list, ~35 ms each) cost ~0.75 s per reload, twice per tap; taps queued seconds of drawing, and taps during a redraw opened the app (7 Oct 2026, L23) |
| S18 | **Widget feedback can't wait for the app.** After an intent that runs in the app's process, iOS shows the widget's reload ~3 s later (3.9–4.1 s against 0.7–0.8 s for the same action run in the widget's process, same run on the iPhone); our own reloads in between aren't shown. So the tap runs in the widget's process and hands over to the app (`OpensIntent` → a `LiveActivityIntent`, run in the background: measured 8 Oct, the app never came to the front), and a `Toggle` gives the first frame. iOS ignores a switch nested in a switch (measured), so a quick second tap needs the fast redraw, not deeper switches. Judge widget speed by what the screen shows (`WidgetLatencyDeviceTests`, screenshots), not by when our code finished | Our code finished in 0.3–0.8 s while the iPhone showed the change after ~4 s (8 Oct 2026, L24) |
| S16 | **Work set off by every data change waits until the changes stop.** Widgets publish 0.5 s after the last change, and at once when the app starts to leave the screen (8 Oct 2026: with 2 s, logging and going straight back to the Home Screen showed the old widget; an update from an app already in the background can be held back by iOS); reminders re-plan 300 ms after. Nothing heavy runs per tap on the main thread. **Every Core call Swift makes runs on the database's background dispatcher** (`offMain`, `withContext(databaseDispatcher)`): Kotlin runs a suspend function on its caller's thread until it first suspends, so a Core class without it merges, parses and counts on the main thread (`CloudStore`, 10 Oct 2026: a 20,000-record iCloud fetch gave Today's +1 eight freezes) | The widgets' month projection ran on every tap: 362 ms, up to 118 ms each (2 Oct) |
| S19 | **A rule answered by the shared Kotlin core tells SwiftUI exactly what the Swift rule it replaced read, and no more** (12 Oct 2026, Current Work 92). SwiftUI can't see inside Kotlin, so each call reads its inputs itself (`access(keyPath:)`, `observeEntries`): the settings for every rule, a habit's logs only for a rule that reads them (never for its goal, its first day or "is it due", except a task or a schedule counted from the last time it was done), a habit's skips, moved days, pauses, goal history and archive days through one counter (`ruleInputs`), Today's cards and times of day only where they're used (`HabitStore+Rules.swift`). Too little and a view stops redrawing (Arrange, run 38216853635); too much and it redraws on every change. **What the rules are given is read untracked** (`ruleState`, `isSaved`'s `_habits`): the view that happens to ask a rule first after a change gives the core its habits and settings again, and read tracked, that view then redrew for every habit, skip, pause, timer and section (the Day sheet drew 641 times where the Swift rules drew it 451, run 38317935766; 13 Oct 2026). Count draws per variant before and after (`Count: …`) | Every shared rule read its habit's logs: Today's list drew 287 times where the Swift rules drew it 69, and the Day sheet's add, edit and undo went from 260 to 467 ms/s of hitches (run 38247029430) |
| S20 | **Swift asks the shared Kotlin core as few times as the screen needs, and the core does each answer's work once** (12 Oct 2026, Current Work 92). Crossing into Kotlin costs ~0.2 µs; what makes a call dear is around it: a strip of days (Progress's cards, the habit page, Over Time, the calendar) asks once per habit and range (`LiveRules.days` → `HabitRules.strip`, read back as one block of bytes), never once per day and rule; the Swift side does one lookup per call (`ruleHabit`, one `ruleInputs` read); the core finds a habit's data once and keeps it on the habit (`HabitFacts`, never a lookup by its ID string: Kotlin on Apple platforms hashes the string again each time), indexes logs by day number (no boxed numbers), reads the clock only when a timer or an overdue task needs it, and isn't given habits and settings again unless one it reads changed. **A Today row asks once** (`LiveRules.row` → `HabitRules.row`, `coreRow`: ten numbers per habit and day), never one call per rule: on the Apple Watch's slower processor ten crossings a row were felt (13 Oct 2026, runs 38342508127, 38342507816). Measure the parts on their own (`rules-calls`, `RulesBench`) and side by side with `-swift-rules` before changing anything | The first switch was 2–3× the Swift rules' work on strips of days and doubled the Day sheet's hitches; the profile put Kotlin's own work at 0.1 % (runs 38229397046, 38247037194, 38289401969) |

**Finding a slow spot:** time and count before changing anything (`perfTimed`; "Count: …" redraw counters, which the bisect lists per variant); measure a
control in the same run (a blank page, a bare text field); bisect with scenario variants when profiles disagree; **choose between two implementations only from variants side by side in one run** (`PerfSwitches`, one scenario each: the same pager measured 5.7 and 61 ms/s of hitches in two separate runs, L22); **call something a regression only from the before and after built in one job and measured in turns, four rounds or more** (`[ios-perf-bisect]`, `Tools/perf/bisect_perf.sh`; 12 Oct 2026: two separate runs on the since-removed Watch app showed the shared rules 4× slower on +1, side by side the gap was a fraction of that, most of it views redrawing for reads they didn't need, S19); the 5 Oct "regression" of Current Work 49 was separate runs on different machines; side by side, nothing had got slower, L29, 8 Oct 2026) (a
profile on the shared Mac can lose 60 % of its samples); look at *when* a freeze happens (opening, first scroll, after a
tap); measure first openings on their own; repeat a surprising number (hosted runs vary 2–3×); test with a year of
history; and confirm on the phone (`iOS/Tools/perf/measure_perf_device.sh`). Keyboards are judged on the phone only (the
first keyboard is 136 ms there, 2.1 s on the simulator: L18).

## D — Data safety (people's data must never be lost)

**21 Oct 2026, the user: phones only, no accounts (D16).** The first launch is the iPhone and Android phones only (no iPad, tablet, Apple Watch, Wear OS or desktop). The iPhone syncs through the person's own iCloud (CloudKit); Android backs up to the person's own Google Drive. No accounts, no Plus Family; Plus stays with the store that sold it and moves between iPhone and Android by hand. Why: [the 21 Oct research](<Research/Research Reports/Market Discovery/Phones Only, No Accounts — Why, 21 October 2026.md>). **10 Oct 2026, the user: no server holds anyone's habits (D16).** Built the same day ([Architecture 11 — iCloud Sync
with CloudKit](<Architecture/11. iCloud Sync with CloudKit.md>), Current Work 81): D3, D4, D9, D12, D14 and D15 now describe
iCloud, each keeping its intent. Why: [Plus, Price and the Server — How We Decided](<Research/Research Reports/Business Model and Monetization/Plus, Price and the Server — How We Decided/README.md>).
