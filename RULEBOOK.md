# The Rulebook

Written by Claude (Claude Code), 3 October 2026, at the user's request: "Everything should be in one place, so that
every agent reads it before implementing anything and avoids the same repeating mistakes."

**Every agent (Claude, Codex or any other) reads this whole file before changing anything in this repository.** It
takes about ten minutes. To point an agent here, say **"read the Rulebook"** or **"follow the Rulebook"**; to point at
one rule, use its number ("that breaks S5").

How it works:

- **Every rule that applies to any change is here, and only here.** Each one exists because a mistake was made once
  and cost something. The *why* (measurements, reviews, incidents) is in the evidence linked at the end of each
  section; read it when a reason is unclear or before arguing for a change.
- **Rule groups:** **S** speed · **D** data safety · **U** design and behaviour · **T** testing · **W** how we work.
- **Widgets are locked (U28):** read [Widgets — Taps and Updates (Locked)](<iOS/Docs/Widgets — Taps and Updates (Locked).md>) before changing anything a widget does.
- **Decisions about one screen** (what it shows, its copy, its layout) are in
  [Design Rules — Don't Regress](<iOS/Design Rules — Don't Regress.md>), one section per screen, and in that screen's
  spec ([iOS/Docs index](<iOS/Docs/README.md>)). Before changing a screen, read its section there too (U12).
- **A rule changes only here,** with the date and the reason. A product rule changes only with the user's say-so.
- **Learned something new** (a mistake, a measurement, a near miss)? Add or sharpen the rule here **the same day**,
  and put the numbers in the evidence file.

## Before a piece of work is done: the checklist

1. `iOS/Tools/perf/check_rules.sh` passes (a second, works on Linux; run it before every push). Never loosen it.
2. The tests for what changed have run and passed, **once, at the end of the piece of work** (T7). A screen or
   `HabitStore` change also gets a speed run (S2).
3. Anything that stores, sends, deletes or moves data meets every D rule.
4. A visual or layout change has been looked at on the real iPhone before it's called done (U9).
5. What you learned is written down: rules here, numbers in the evidence, the user's points ticked in their checklist.

## S — Speed (top priority: a change that makes the app slower is not finished, however it looks)

**Targets** (GitHub's simulator, a year of history): hitch time under **5 ms/s** while scrolling, tapping or typing;
**no freeze of 100 ms** or more; **opening a screen adds under 50 ms** to a blank page pushed the same way in the same
run (the hosted simulator's push alone is 120–200 ms; the iPhone 16's 45–85 ms). **The phone has the final word.**

| # | Rule | The mistake behind it |
|---|---|---|
| S1 | **The phone build is optimised.** The user installs *Debug* from Xcode, so Debug keeps `SWIFT_OPTIMIZATION_LEVEL = -O` and `KOTLIN_FRAMEWORK_BUILD_TYPE = release` | Every screen ran several times slower unoptimised (L1) |
| S2 | **Measure; never judge speed by eye, screenshots or reasoning.** Speed runs (`[ios-perf]`): the app drives itself (`PerfDriver`, a scenario per screen and interaction, handled with `.onPerfCommand`), records its own stalls (`MainThreadMeter`) and times suspect work (`perfTimed`, the "Timed work" table). Never measure through XCUITest. Typing goes through the focused field's `insertText`/`deleteBackward`, never by replacing the Binding | Screenshots and XCUITest showed freezes that weren't there and hid real ones (L2, L3) |
| S3 | **Only the smallest view that shows the time ticks** (a running row's clock, the timer bar, the player's clock). Never a `TimelineView`, `Timer` or ticking `@State` around a screen or list, not even once a minute: keep the time in `@State` and move it with a `.task` that sleeps until the next moment that matters | Today redrew every row every second; a once-a-minute ticker made scrolling 55 % busy (L4) |
| S4 | **A `TimelineView` is anchored at a fixed date**, never `.now` or `.distantPast`, and a view never switches between a `TimelineView` and a plain view (pause = a schedule that never ticks) | The app froze; the player's circle faded on Pause (L5) |
| S5 | **Anything that walks days or history is worked out once in `HabitStore` and remembered** (`streak`, `bestStreak`, `daySummary`, `placements`); never in a view's `body`. Read one habit's entries (`entries(of:)`), never every entry. Change entries only with `insertEntry` / `removeEntry(at:)` / `replaceEntry(_:at:)`. Keep the coalesced `entries` notification (one per main-actor turn) and the in-place `_modify` accessor | One tap recalculated every row's streak over a year (L6) |
| S6 | **Keep what a redraw touches small.** State that changes while scrolling lives in its own small `@Observable` read only by the view that needs it. A value read by every row is read in the smallest view that uses it. A covered screen stops drawing and its clocks pause. Stable view identities: never `.id(UUID())` | Each row's appearance rebuilt Today; Today redrew behind the player and under menu pages (L9, L15, L16) |
| S7 | **A tap changes the screen at once; the database write follows** (`addLogged`, `removeLogged`, `toggleTimer`). On a failed write, reload and say so. Never make a tap wait for storage. **A reload never hides a tap shown but not yet written:** a reload with writes queued behind it reloads again after the last of them (`reloadAfterSync`), and data is shown only once it's saved (`seedDemo`) (8 Oct 2026) | Quick taps landed on the old state (L14); a ▶ tapped as the demo data appeared was wiped by its reload (TimerUITests, run 37763470033) |
| S8 | **`body` stays cheap:** no sorting or filtering of history, no `Calendar` arithmetic in loops (`LocalDay.adding(days:)`, `weekday`), no formatter or big string built per row (make it once and keep it) | A `NumberFormatter` per number was most of a row's time (L7) |
| S9 | **In a `List` with a selection, use `NavigationLink { Page() } label: { … }`**, not `NavigationLink(value:)` | The habit page never opened from All Habits |
| S10 | **Rows stay light.** A shadow only on a background shape, never on text, never a `.clear` shadow; one `.sheet(item:)` per row; no `GeometryReader` just to size a fill (`scaleEffect(x:anchor:)`); **no `ViewThatFits` in a row** (it lays out every option; choose the layout from `dynamicTypeSize` instead) | Every Today row paid an offscreen pass, four sheets and a geometry pass (L13); the after-log line's `ViewThatFits` doubled the cost of changing days (L21) |
| S11 | **Typing updates only the field.** The typed text lives in a small `@Observable` read only by the field, **and the field's binding is made in the field's own view** (`DraftTextField`, `NameField`). The form reads only "is it valid / is there a name". Anything that follows the text catches up when typing pauses (0.3 s); saving reads the live text. Never animate per keystroke | The habit form rebuilt per letter (92 % busy); the entry editor cost 24 ms/s against a bare field's 0 (L8) |
| S12 | **Charts are drawn in one pass** (`LightBarChart`, `LightLineChart`: one `Canvas`, every bar for VoiceOver, a chart descriptor for Audio Graphs). No Swift Charts in a screen that scrolls | A 1–2.7 s freeze the first time the habit page reached its chart (L10) |
| S13 | **Never a lazy grid (`LazyVGrid`/`LazyHGrid`) inside a `List` or `Form` row.** Use a plain `Grid` sized up front; lazy grids only in a `ScrollView` | Opening any habit's page crashed the app on the iPhone (L19) |
| S14 | **Ids in one lazy grid are one type** (an enum: `.weekday(i)`, `.place(i)`), and cells whose places are fixed are keyed by position, not content | Days 1–6 of every month were never drawn; cells slid on a month change (L11, L12) |
| S15 | **No `UserDefaults` write on every data change.** Write only when the value changes, or keep it in memory and save on leaving the app | The Day sheet: 535 ms/s and 36 freezes (L17) |
| S17 | **A widget timeline holds only the next few hours** (`PhoneWidgetTimeline.horizon`, 3 h) **and the next day's start; entries at least 5 minutes apart.** WidgetKit draws every entry the moment it gets a timeline, before showing anything; the snapshot's seven days carry the widget through days without the app, one short timeline at a time. No `.invalidatableContent()` on a widget's buttons (any tap dims every marked view: the rows flickered). A widget tap reloads at once, without the 250 ms coalescing. Measure widget speed on the iPhone with `WidgetLatencyDeviceTests` and the opt-in `-widget-timing on` log, never by polling the Home Screen's whole element tree (one read took ~43 s) | A week of entries (21 for a Medium list, ~35 ms each) cost ~0.75 s per reload, twice per tap; taps queued seconds of drawing, and taps during a redraw opened the app (7 Oct 2026, L23) |
| S18 | **Widget feedback can't wait for the app.** After an intent that runs in the app's process, iOS shows the widget's reload ~3 s later (3.9–4.1 s against 0.7–0.8 s for the same action run in the widget's process, same run on the iPhone); our own reloads in between aren't shown. So the tap runs in the widget's process and hands over to the app (`OpensIntent` → a `LiveActivityIntent`, run in the background: measured 8 Oct, the app never came to the front), and a `Toggle` gives the first frame. iOS ignores a switch nested in a switch (measured), so a quick second tap needs the fast redraw, not deeper switches. Judge widget speed by what the screen shows (`WidgetLatencyDeviceTests`, screenshots), not by when our code finished | Our code finished in 0.3–0.8 s while the iPhone showed the change after ~4 s (8 Oct 2026, L24) |
| S16 | **Work set off by every data change waits until the changes stop.** Widgets publish 0.5 s after the last change, and at once when the app starts to leave the screen (8 Oct 2026: with 2 s, logging and going straight back to the Home Screen showed the old widget; an update from an app already in the background can be held back by iOS); reminders re-plan 300 ms after. Nothing heavy runs per tap on the main thread. **Every Core call Swift makes runs on the database's background dispatcher** (`offMain`, `withContext(databaseDispatcher)`): Kotlin runs a suspend function on its caller's thread until it first suspends, so a Core class without it merges, parses and counts on the main thread (`CloudStore`, 10 Oct 2026: a 20,000-record iCloud fetch gave Today's +1 eight freezes) | The widgets' month projection ran on every tap: 362 ms, up to 118 ms each (2 Oct) |

**Finding a slow spot:** time and count before changing anything (`perfTimed`; "Count: …" redraw counters); measure a
control in the same run (a blank page, a bare text field); bisect with scenario variants when profiles disagree; **choose between two implementations only from variants side by side in one run** (`PerfSwitches`, one scenario each: the same pager measured 5.7 and 61 ms/s of hitches in two separate runs, L22); **call something a regression only from the before and after built in one job and measured in turns, four rounds or more** (`[ios-perf-bisect]`, `Tools/perf/bisect_perf.sh`: the 5 Oct "regression" of Current Work 49 was separate runs on different machines; side by side, nothing had got slower, L29, 8 Oct 2026) (a
profile on the shared Mac can lose 60 % of its samples); look at *when* a freeze happens (opening, first scroll, after a
tap); measure first openings on their own; repeat a surprising number (hosted runs vary 2–3×); test with a year of
history; and confirm on the phone (`iOS/Tools/perf/measure_perf_device.sh`). Keyboards are judged on the phone only (the
first keyboard is 136 ms there, 2.1 s on the simulator: L18).

*Evidence:* [PERFORMANCE-LESSONS.md](iOS/PERFORMANCE-LESSONS.md) (lessons L1–L19 with every number, the iPhone
results, what's still open) · `iOS/Tools/perf/` (scripts) · the speed tables on the `ci-results` branch.

## D — Data safety (people's data must never be lost)

**10 Oct 2026, the user: no server holds anyone's habits (D16).** Built the same day ([Architecture 11 — iCloud Sync
with CloudKit](<Architecture/11. iCloud Sync with CloudKit.md>), Current Work 81): D3, D4, D9, D12, D14 and D15 now describe
iCloud, each keeping its intent. Why: [Plus, Price and the Server — How We Decided](<Research/Research Reports/Business Model and Monetization/Plus, Price and the Server — How We Decided/README.md>).

| # | Rule | Why |
|---|---|---|
| D1 | **The phone's own database is the source of truth; everything works offline.** The server only syncs and backs up | Online-only apps lose people the moment the network or server fails |
| D2 | **Every database upgrade is tested from every past version, keeps a copy first, and never resets on error** (a column added only if missing; `MigrationTest`) | An update that wiped data is the most damaging failure in 1.5 M reviews (53.9 % 1★) |
| D3 | **Another Apple Account, or iCloud data that was removed, asks first and never deletes** (Architecture 11 §10–11, built 10 Oct 2026). iCloud on a different Apple Account: nothing is uploaded or deleted until the person chooses Add to This Account's iCloud (a merge by ID; nothing replaced) or Keep on This iPhone Only. The app's iCloud data deleted by the person or another device: "Back up to iCloud again?" before anything goes up. A sign-out, a full iCloud or a deleted zone never deletes anything on the phone (Apple's sample code does: never copy that) | Sign-ins that wiped or swapped data; 13 of 44 hand-read reviews of iCloud sync failing: a bad or empty state reached every copy (Architecture 11 §3) |
| D4 | **Backup is automatic, on by default, free and visible.** With iCloud on, **every change syncs to the person's own iCloud** (CloudKit, `CloudSync`), and **dated backup files are kept apart from sync** in their iCloud Drive: per device, the last 7 days, 4 weeks and 6 months (`BackupFolder`), within a size budget, never fewer than 3; backed up as you go (on leaving the app when something changed, at least 10 minutes apart; after a widget or notification log; at least daily). Someone who keeps iCloud off can use Google Drive, kept exactly as built (the user, 10 Oct 2026). The iCloud page always says the truth: synced (when), waiting (how many), iCloud full, off, bringing habits in; a problem shows a card on Today. **The free plan syncs one device at a time** (`activeDevice`; Move Here, saved only if unchanged), Plus every device; **the old device sends what it has before it stops** (Architecture 11 §12). **No backup ever replaces a copy that has habits with an empty or much smaller one** (kept aside as `before-shrink`), and a fresh install sends nothing to iCloud and backs up nothing until its welcome is finished. **An iCloud file not on this iPhone yet is never taken for "no backup" or written over:** Restore asks iCloud's own list (`ICloudLookup`) and waits for it, and a file still in iCloud (a `.icloud` stand-in or a file with no data, `BackupFolder.place`) counts as coming (10 Oct 2026, Current Work 75). A backup counts only once it's read back and its checksum matches | Backups that were hidden, manual, paid or silently broken; sync that stopped and said nothing (14 of 44 iCloud reviews); a reinstalled iPhone's first launch writes its empty database over its own iCloud copy |
| D5 | **Restore is round-trip tested; every export can be imported; a restore keeps an undo file** (30 days). **A backup with nothing in it is never shown as restored**: say so instead (9 Oct 2026) | Restores that failed or brought back half; in the simulator a transfer of an empty backup "succeeded" onto an empty Today (Current Work 73.1) |
| D6 | **Deleting is archiving, with undo.** Schedules and goals change from an effective date and keep their past; streaks are computed from records, never stored | Edits that rewrote history; streaks reset wrongly |
| D7 | **A day is the local calendar day at the moment of logging.** Day start and week start apply everywhere or nowhere; never subtract hours from a moment. **"Today" is `store.today()`, never `Date.now` or `Calendar.current`'s today**, in forms too (6 Oct 2026: a habit added after midnight, before a 3 AM day start, started "tomorrow" and stayed off Today) | Check-ins moved to the wrong day on time-zone and daylight-saving changes |
| D8 | **A test launch never touches the person's data.** `-uitest` runs on an in-memory database as its own store ("uitest"), with its own backup state and folder, and every test launch (`-uitest`, `-dbname`) has its own fake iCloud (`FakeCloud`: signed out unless `-test-cloud` asks), never the person's. Anything new that stores or sends data does the same for test launches. **A test launch keeps its widget files in an App Group folder of its own (`WidgetDisk.directory`), and the person's settings are held aside by the first test launch and put back, exactly, by the next ordinary launch (`TestLaunchIsolation`); `-reset-db` never deletes the person's own database on a real iPhone** (8 Oct 2026, Current Work 74: a test run on the iPhone showed demo habits on the person's widgets, reset their Hide Completed and could have saved and removed their waiting widget taps) | A test run on the iPhone could have synced or backed up demo habits over the person's own (found 2 Oct) |
| D9 | **"Delete My Data From iCloud" removes everything there, deliberately, and only that** (Architecture 11 §17, built 10 Oct 2026). Both CloudKit zones and the app's iCloud Drive backup files go, for every device on the Apple Account; this phone keeps everything unless the person also chooses to erase it, and nothing goes to iCloud again until they turn it on. It's the only CloudKit deletion the app ever makes; it asks first and offers a backup file. "Erase All My Data" turns iCloud sync off on that phone first, so the erased habits don't come straight back | App Review 5.1.1(v); people who couldn't get rid of their data |
| D10 | **Data is never held hostage:** backup, export and sync of what someone has are free, and an ended purchase never hides data | Paywalled data drove 1★ reviews |
| D12 | **A change made outside the app reaches iCloud without the app being opened** (8 Oct 2026, Current Work 67; Architecture 11 §15). Anything that changes data from a widget, a notification, the Live Activity, or just before the person leaves the app goes through `CloudSync.scheduleSoon`, which holds `beginBackgroundTask` until CloudKit has it; batched: 2 s of quiet in the background, 3 s in front, never more than 10 s. **A change leaves the outbox only when CloudKit confirms a record built after it was queued** (by outbox position, never by stamp: an op whose fields all lost the merge carries a newer stamp than its record, and waited for ever; found by the property test, 10 Oct 2026); every launch and return puts every waiting row back on the engine's queue (it drops items on a full iCloud). Fetched changes are merged in one transaction before the engine moves on. A failed send keeps everything in the outbox and asks for a background retry. Never call the engine from inside one of its own events | Five widget taps were saved but never sent: iOS suspended the app inside the 3 s wait (PERFORMANCE-LESSONS L25) |
| D13 | **Anything that acts from outside the app works on a locked iPhone and never crashes the app behind it** (8 Oct 2026, Current Work 69–70). Every intent behind a widget, Live Activity, alarm or notification button sets `authenticationPolicy = .alwaysAllowed`; the notification delegate runs on the main actor (never `nonisolated` async methods: UIKit stops the app when "finished" comes from a background thread). Check each on the iPhone with the phone locked, and check its crash logs (`devicectl … --domain-type systemCrashLogs`) | The Live Activity's Pause and an alarm's Done asked for Face ID; every reminder Done/+1 crashed the app after saving, so its sync was lost until the app opened (PERFORMANCE-LESSONS L26) |
| D14 | **A phone with an empty or new database gets everything back from iCloud first** (Architecture 11 §13.1). A fresh install fetches before offering Start without restoring, sends nothing until its welcome is finished, and merges by ID, so a reinstall's rows come back and are never doubled. A lost engine state fetches everything again (merges are idempotent). In Debug builds demo data is never added on a phone signed in to iCloud. A phone restored from another's backup gets its own clock node (`identifierForVendor` changed) | A reinstalled iPhone synced "OK" and got nothing (PERFORMANCE-LESSONS L28); 9 of 44 iCloud reviews: lost on a new phone or a reinstall |
| D15 | **A new iPhone or iPad gets everything from iCloud; another platform uses Export and Import** (Architecture 11 §17). Moving with a code through our server went with the server (D16). A checked backup file (Export, then Import with its preview and undo, D5) moves habits anywhere, iCloud or not | The local-network transfer needed both phones together; the code transfer needed our server |
| D11 | **Secrets never go in the repository or a chat.** Keys go in with `wrangler secret put`; the `.p8` stays with the user; the server never logs request bodies or tokens. **The repository is public**: no secrets, no other apps' or designers' images in git | — |
| D16 | **No server of ours holds anyone's habits** (the user, 10 Oct 2026, final). **Apple first:** sync and backup through the person's own iCloud (CloudKit private database with `CKSyncEngine`), Plus from StoreKit, Plus Family through Apple's Family Sharing. **Android after:** Android's own Auto Backup and a daily file in the person's Google Drive, free; sync between Android devices through their Google Drive (a mailbox of per-device change files merged by `SyncRules`) only after a two-device prototype passes, built after the CloudKit work. The only server is an entitlement record, so Plus bought on one store reaches the other, added when Android launches; it never holds habits and a purchase never depends on it. **Full privacy:** habits live only on the person's devices and in their own iCloud or Google Drive; we never see them | A one-time price can't carry a server we'd pay for over decades: with inflation and Apple at 30%, an extreme user's $24.99 sale lost money as built ([price report](<Research/Research Reports/Business Model and Monetization/Plus, Price and the Server — How We Decided/Plus and Plus Family — Price and Size from the Extreme Case.md>) §4) |
| D17 | **The mass-change brake, both ways** (the user, 10 Oct 2026; Architecture 11 §13.2). This device's deletes waiting to go to iCloud wait for the person when they're more than 50 rows not from one action the person confirmed, or more than 20% of the habits and records (from 10 rows: below that, 20% is one or two taps). Fetched deletes past 20% of the habits and records are held, whole, in the database, and nothing else is applied or sent meanwhile; the iCloud page asks, with Restore From a Backup one tap away. A restore the person confirmed with Replace is one explicit action | 13 of 44 iCloud reviews: a bug, an update or an empty phone spread "nothing" to every copy |

*Evidence:* [Data Safety — Every Way Users Lose Data, and the Rules That Prevent It](<Research/Research Reports/Data, Sync and Accounts/Data Safety — Every Way Users Lose Data, and the Rules That Prevent It.md>)
(Part 1: the 15 worst failures; Part 5: rules 1–17) · [Data Safety, Accounts and Sync](<Architecture/Data Safety, Accounts and Sync.md>)
(the architecture) · [server/README.md](server/README.md) (accounts, deletion, Apple sign-in revocation, releases).

## U — Design and behaviour

| # | Rule | Why |
|---|---|---|
| U1 | **Native iOS only:** SwiftUI components, SF Symbols, system fonts; light and dark; Dynamic Type up to the accessibility sizes; a VoiceOver label on everything that means something | The app is meant to feel like part of the iPhone |
| U2 | **Colour belongs to the habits; the chrome is monochrome.** Switches are the iPhone's green and edit-mode selection its blue (the ink tint is unreadable on them in dark mode). A `Toggle` inside a `Menu` sets `.toggleStyle(.automatic)`. **6 Oct widget correction:** Today row/widget CTAs use neutral `tertiarySystemFill` and ink before completion; genuine positive completion uses the habit's main color with white content, matching `RoundActionButton`. Keep add labels meaningful after completion, running timers neutral, and quit/limit controls out of the completed treatment. Do not make every row action primary black/white. | Near-white switches; menu toggles that stopped responding (2 Oct); the user's 6 Oct rejection of heavy CTAs in both single-habit and Large Today widgets |
| U3 | **Nothing counts against anyone.** Never red; never "missed", "failed", "relapse", "reset", "due" or "overdue". Skipped, paused and not-its-day days are neutral | Shame language drives people away |
| U4 | **Nothing on Today moves during a run of taps** (`TodayLayout.hold`; things settle 1.5 s after the last tap); feedback comes from the tap, never from a redraw | Rows jumped under people's fingers |
| U5 | **A new feature never removes an old one** without listing what the old view showed and keeping each item, or saying why it goes | Adding ▶ deleted "N left" |
| U6 | **Text:** names and checklist items 24 characters, times of day 16, units 12 (`TextLimit`, `limitText`); never `.fixedSize()` a text field; every typing field stays above the keyboard. A value cut back while a field is changing is put back on the next turn, or the field keeps showing what wasn't kept | Clipped and hidden fields; a name field showed 39 letters while 24 were kept (3 Oct) |
| U7 | **Never put `.toolbar`, `.onChange` or `.task` on a Form `Section`** (it repeats per row); a pushed screen keeps its own `@FocusState` | Four Next buttons on one keyboard |
| U8 | **One app, one set of IDs:** Often Enough, `com.oftenenough.app` ([App Identity](<Architecture/App Identity — Name, Domain and IDs.md>)); replace any leftover `com.lalithsaicharan.habits` | Mixed IDs break signing, widgets and purchases |
| U9 | **Check every visual or layout change on the real iPhone before calling it done.** **6 Oct widget-design checks:** measure full header/page/logging hit regions and the final rendered text/progress geometry; a successful nested Figma instance resize can leave the original dimensions unchanged. Use actual reflow or scoped source-state components, then audit/render the result. Font getter metadata may contain variation axes rejected by the setter: verify/load supported family/style descriptors before creating measurement text (6 Oct recovery audit). Figma verification remains distinct from native/device acceptance | The habit-page crash and the unreadable switches never showed on the simulator (2 Oct); Medium widget instance geometry ignored progress-size overrides and clipped larger text before rendered checks caught it (6 Oct) |
| U10 | **Progress only reads; its overview counts habits, not ticks** | It must agree with Today's day bar |
| U11 | **Words:** say it the way people do ("Log time manually", "For today", "Planned for Wed 1 Oct"); see Design Rules' "Words the app never uses" | Copy that confused people |
| U12 | **Before changing a screen, read its section in Design Rules and its spec** | Per-screen decisions that agents undid |
| U13 | **Order is the person's own.** Nothing reorders itself: not reminder times, a new day, a sync or an edit. New habits and tasks go to the end of their section; sorting is a one-off action; **done habits move below the rest, only after the pause** (U4; the user's final call, 3 Oct 2026, after a day of "stay in place"; Appearance → Done Habits → Stay in Place keeps them where they are). Timed sections follow their times; Anytime and Quitting are placed by the person (the user, 3 Oct 2026) | 35 of 179 order reviews: "the app reshuffles my list" (report 27). 90 of 243 want done rows to sink, 7 kept (report "Ticking Off"): the default sinks, the option keeps |
| U14 | **A row's gestures follow one model, the iPhone's own.** Tap the round control to act, the row to open (its Day sheet, for the day shown). **✓ toggles a once-a-day tick; + adds an amount and never takes back. A check habit always shows ✓, even counted several times a day or N times a week, month or year: there each ✓ adds one check and never takes one back** (the user, 7 Oct 2026: a person who chose a check habit never sees it turned into a +1 counter; Today and widgets alike); **the round button fills, and the completion sound plays, only when the goal is met** (today's for several a day; the period's for a week or month goal, which has no daily goal), so a week goal isn't shown finished after one tap today (the user, 6 Oct 2026). Swipes *reveal* labelled buttons and **never act by themselves, however far they go**; two at most a side: left Skip (Log Slip on a quit row) at the edge, then Note; right a named Undo (the user, 4 Oct 2026: a long swipe opened Note, and three buttons needed a careful swipe; report "Swipe Actions — Reveal, Never Act"). Pause is in the long-press menu and the Day sheet. **Undo always names what it takes back** ("Undo +1 glass"), one entry, never the day; **a checklist step's is "Undo Last Step"**, never the step's own name, and **the after-log line never runs past the row** (Undo shortens with … before anything is pushed out) (the user, 9 Oct 2026: a long step name pushed Add Note off the screen). **Delete is never on a swipe or in view**: it's in a ⋯ menu that asks first and offers Archive | Can't un-check (33 reviews, 2.97★), a second tap doing something else (15, 2.80★), swipes that act unseen (35 accidental, 14 "which way"), deletes too easy (79) yet unfindable (63): report "Today's Rows", 3 Oct. A swipe that acted on its own (≈15), three buttons behind one swipe (`6152463760`): report "Swipe Actions", 4 Oct |
| U15 | **In the Day sheet, Skip and Undo skip keep one place.** Skipping changes only that day's state: the Skip button becomes Undo skip where it was. Keep the usual logging controls visible but disabled; keep saved logs and the day note visible and the note editable. ## T — Testing

| T1 | **Builds and tests run on GitHub Actions, never on the user's MacBook** (battery); cloud sessions are Linux, with no Xcode. `[ios-ci]` and `[ios-perf]` in a commit message, or run the workflow with `tests`, `perf` and `scenarios`. **Minutes are free and unlimited** (public repo), but a job stops at 60 minutes, and a branch keeps only **one** waiting run (a third cancels it). **A cancelled run still counts until it shows completed:** queueing two more while it winds down silently cancelled one of them (4 Oct 2026); queue one, or wait. **Queue the next run only when nothing is waiting on that branch, by hand:** a script that counted active runs read one momentary empty answer from the API and queued two runs too many, which cancelled two waiting groups of the full test of `main` (5 Oct 2026). **Keep a run to six or seven UI classes**: nine (habit creation, scenarios, sync, analytics and others) hit the 60 minutes and were cancelled (6 Oct 2026). **The full speed run no longer fits either:** run `PerfDriver` scenarios in batches of about 20 through a dispatch's `scenarios` (all ~40 were cancelled at 60 minutes; PERFORMANCE-LESSONS L30, 10 Oct 2026). **A run cancelled after ~15 minutes with no runner (`runner_id` 0) never started:** check githubstatus.com before re-running (an Actions outage, 5 Oct). **Two runs finishing together can lose one summary push:** then read that job's "UI tests" step.
